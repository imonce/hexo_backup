> 这份术语表不是按字母序排的。因为**懂这些词的关键不是记住定义，而是知道它们串成几条链**——串错了链，AI 方案在 POC 阶段就会撞墙。

## 导语

面向 AI 落地工程师，半导体产线有三个"看不懂"：

1. **术语看不懂**：ADC、OCAP、FDC 混着讲，不知道谁是谁的上游；
2. **链路看不懂**：拿到了设备数据，但不知道它该进 SPC 还是 FDC，也不知道异常之后谁接手；
3. **边界看不懂**：模型准确率 99%，工艺工程师一句"这个我不能签字"就打回来了。

<!-- more -->
本文按**链路顺序**重排 13 个术语，而不是按字母序。理由很简单：**在半导体产线里，决定一个 AI 方案能不能落地的，往往不是算法，而是它挂在链路的哪个位置**。

> **一个前置说明**：这 13 个词里，12 个是半导体/质量管理术语，`Dify` 不是——它是 LLM 应用开发平台，出现在这份清单里说明受众在做"AI 应用层"的落地。本文会明确把它放在最后一节，并说明它和前面 12 个词的关系（以及不该有的关系）。
>
> **另一处诚实说明**：`COA` 在半导体语境下有歧义（见 1.4）。本文按最常见的 `Certificate of Analysis` 展开，如果你的产线用它指别的东西，请以内部定义为准。

## 0. 先定位：13 个术语分别在哪一层

用 ISA-95 的分层先给出坐标系（这套分层的价值在于：**跨层通信是产线数字化的主要成本来源**）：

```
┌──────────────────────────────────────────────────────────────┐
│ L4  ERP / 经营层                                              │
│     APQP（先期质量策划，跨 L4-L3 的流程）                     │
├──────────────────────────────────────────────────────────────┤
│ L3  MES（制造执行）                                           │
│     工单派发 · WIP 追踪 · 谱系(genealogy) · Recipe 管理       │
│     SPC（过程控制，统计侧）· OCAP（异常处置）· 8D（问题闭环） │
│     SOP（作业标准，跨 L3-L1 的文档）                          │
├──────────────────────────────────────────────────────────────┤
│ L2  EAP / SCADA（设备自动化与数据采集）                       │
│     SECS/GEM 通信 · Recipe 上下载 · Trace 采集 · 告警         │
│     FDC（设备侧实时监控，跨 L2-L3）                           │
│     ADC（缺陷分类，跨 L2-L3）                                 │
├──────────────────────────────────────────────────────────────┤
│ L1  设备控制（PLC / 运动控制 / 工艺模块）                     │
│     AOI（光学检测，在线设备）                                 │
├──────────────────────────────────────────────────────────────┤
│ L0  传感器 / 执行器                                           │
│     DOE（实验设计，是方法论，不占某一层）                     │
└──────────────────────────────────────────────────────────────┘
                  ↕
Dify（AI 应用层 / LLM 编排，横跨 L3-L4）
```

这张图最重要的信息是**四个"跨层"标记**：

| 术语 | 跨哪几层 | 为什么跨层很重要 |
|---|---|---|
| **APQP** | L4 ↔ L3 | 它是"产品导入期的流程"，决定了后面所有控制项 |
| **FDC** | L2 ↔ L3 | 数据在设备侧，判定与处置在 MES 侧 |
| **ADC** | L1 ↔ L3 | 图像在设备侧，缺陷分类结果要进良率系统 |
| **SOP** | L3 ↔ L1 | 文档在系统里，执行在工位上 |

**跨层的术语，就是 AI 落地时最容易出问题的地方**——因为数据、模型、决策权分属不同团队。

## 1. 术语逐条拆（按链路顺序）

### 1.1 MES：产线的"账本 + 调度台"

**全称**：Manufacturing Execution System，制造执行系统。

**它做什么**（不要只记"制造执行"，要记四件事）：

| 功能 | 具体内容 | 没有它会怎样 |
|---|---|---|
| **工单与派工** | 哪个 lot 在哪台机台、用什么 recipe、什么优先级 | 靠人喊，排产靠 Excel |
| **WIP 追踪** | 每片/每批在制品的当前位置与状态 | 找不到货，交期承诺不可信 |
| **谱系（Genealogy）** | 这片 wafer 经过了哪些机台、哪些腔体、哪些批次材料 | **出问题时无法界定受影响范围（召回/hold 范围算不出来）** |
| **Recipe 管理** | 工艺配方的版本、审批、下发 | 版本混乱，改错参数无人知 |

**半导体场景的特殊性**：

- **Lot / Wafer / Die 三级粒度**：MES 要同时管 batch（炉管 25 片一批）、single-wafer（单片处理）、die（封装前的单个芯片）；
- **Rework / 返工路径**：不良品可以重工，重工后谱系要能追溯（不然良率分析会把重工品和正常品混在一起）；
- **Bank / Hold 机制**：任何异常（SPC OOC、FDC alarm、设备故障）都会把 lot 置为 hold，等工程判断。**这是"异常闭环"在系统上的物理落点。**

**对 AI 工程师最重要的一点**：**MES 是"标签"的来源**。你要做良率预测、缺陷归因，最终都要 join 回 MES 的谱系表才能知道"这片 wafer 走了哪条路径"。**没有谱系，你的特征工程就只能做到"当前机台"这一层。**

### 1.2 EAP：设备与系统的"翻译官"

**全称**：Equipment Automation Program，设备自动化程序。

**它是干什么的**（一句话）：**把设备的私有接口，翻译成 MES 能听懂的标准消息。**

```
MES ──(标准命令)──> EAP ──(SECS/GEM)──> 设备
                      ↑
                 协议转换 + 状态机 + 数据缓存
```

**EAP 承担的六件事**：

| 能力 | 说明 |
|---|---|
| **通信协议栈** | SECS-I / HSMS（TCP）、SECS-II（消息内容）、GEM（行为模型） |
| **远程命令** | MES 下发 START / STOP / PAUSE / RESUME / PP-SELECT |
| **Recipe 管理** | Recipe 上传/下载/比对（防止机台上跑的不是 MES 认为的那个版本） |
| **数据采集** | 实时事件（event）、报警（alarm）、**Trace 数据（传感器时序）** |
| **状态上报** | 设备状态机（Idle / Running / Down / Engineering…） |
| **载具/基板追踪** | Carrier、Substrate 的位置与状态 |

**必须知道的 SEMI 标准编号**（这是和这家客户对话的"入场券"）：

| 标准 | 内容 | 工程意义 |
|---|---|---|
| **E4** | SECS-I（串口传输） | 老设备还在用 |
| **E37** | HSMS（TCP/IP 传输） | 新设备主流 |
| **E5** | SECS-II（消息语义、Stream/Function） | 例如 `S1F1` 是"你在吗" |
| **E30** | GEM（通用设备模型） | 定义了状态机、报警、变量、事件的标准行为 |
| **E40 / E94** | Process Job / Control Job | 批次作业与控制的抽象 |
| **E87 / E90** | Carrier / Substrate Tracking | 载具与基板追踪 |
| **E10 / E79** | 设备 RAM（可靠性/可用性/可维护性）、OEE | 设备效率指标的标准化定义 |
| **E116** | EPT（设备性能追踪） | 更细的性能指标采集 |

**踩坑提醒（这一段是 AI 工程师最该看的）**：

1. **Trace 数据的采样率不统一**。有的设备 1Hz，有的 10Hz，有的"事件触发式"（只在数值变化超过阈值时上报）。**做时序模型前必须先做重采样与对齐**，否则多机台的特征没法拼。
2. **Timestamp 不可信**。设备时钟与 MES 时钟常有秒级偏移，跨设备关联时会错位。要么做 NTP 同步，要么用"事件索引"而非绝对时间对齐。
3. **Trace 变量名是设备厂商私有的**。同一物理量（如腔体压力）在不同厂商设备上叫不同名字（`ChamberPressure` / `PRESS_CH` / `VAC_1`）。**没有统一的变量字典，你的模型只能一台机器一个模型。**
4. **不是所有设备都开 Trace**。老设备可能只能采 event，拿不到时序。**这决定了你的方案能不能规模化。**

**一句话定位**：EAP 是**数据的地基**。地基不稳（采样不齐、时间不同步、变量名不统一），上面的 FDC/SPC/AI 全是空中楼阁。

### 1.3 AOI：在线光学"找不同"

**全称**：Automated Optical Inspection，自动光学检测。

**机制**（比"拍照找缺陷"要具体）：

```
1. 成像：线扫相机/面阵相机 + 多角度光源（明场/暗场）
2. 对准：与"黄金参考"（golden reference）做配准
   - 类型 A：Die-to-Die（相邻 die 互比）
   - 类型 B：Die-to-Database（与设计版图比）
3. 差分：算图像差异，超阈值的区域标为"缺陷候选"（defect candidate）
4. 输出：缺陷坐标 + 尺寸 + 图像 patch + 粗分类
```

**它最强的能力**：**快 + 全检**。人眼看 1% 抽样，AOI 可以 100% 全检，且速度是人的几十倍。

**它最大的问题（这是 AI 的第一个机会）**：

> **AOI 的"缺陷候选"里，大量是误报（false call / nuisance）。**

业界常见情况（**范围性表述，随产品、工艺节点、算法版本差异极大**）：AOI 报出的候选里，**30%–70% 需要人工复判（review）才能确认是否真缺陷**。

这意味着：

- 复判是**人力瓶颈**（一条先进封装线可能需要几十人做复判）；
- 复判是**一致性瓶颈**（不同人判定不同）；
- 复判是**节拍瓶颈**（AOI 几秒出一片，人看一片要几分钟）。

**这个结构性矛盾，就是"AI 做误报过滤"的 ROI 来源**。下面 4.1 会展开。

### 1.4 ADC：给缺陷"贴标签"

**全称**：Automatic Defect Classification，自动缺陷分类。

> **术语歧义提示**：在**设备电气**语境里，ADC 是 Analog-to-Digital Converter（模数转换器，EAP 采数据时常见）。在**质量/检测**语境里，ADC 是 Automatic Defect Classification。这两者同缩写不同物，看上下文区分。本文按后者讲。

**它在链路里的位置**：

```
AOI（或 e-beam 复检 SEM）→ 缺陷候选 → ADC → 缺陷类别（bin code）
                                              ↓
                                        良率分析 / 缺陷 Pareto / 根因
```

**两种技术路线**：

| 路线 | 机制 | 优点 | 缺点 |
|---|---|---|---|
| **RB-ADC**（Rule-Based） | 用缺陷属性（尺寸、极性、灰度、位置、长宽比、邻域特征）做规则分类 | 可解释、无需训练数据、稳定 | 规则难覆盖长尾；换产品要重写规则 |
| **AI-ADC**（Deep Learning） | 直接对缺陷图像 patch 做 CNN/ViT 分类 | 可覆盖长尾、跨产品迁移 | 需要标注数据；黑箱；类别不平衡严重 |

**关键工程点**：

1. **bin code 体系是客户定义的**，不是通用的。同一类"颗粒"在不同 fab 可能分成三种 bin（按尺寸/位置/来源）。**你的模型输出必须映射到客户的 bin 体系，否则结果无法进入既有报表。**
2. **类别极度不平衡**：常见缺陷（particle、scratch）占 90%+，致命缺陷（void、delamination）可能 < 1%。**用 accuracy 评估是自欺欺人，必须看 per-class recall + 混淆矩阵。**
3. **标注质量决定上限**。缺陷分类的标注依赖 SEM 复检 + 工程师判断，**标注者间一致性（inter-annotator agreement）往往不高**。做模型前先算一下标注一致性——如果 kappa < 0.6，你的"99% 准确率"没有意义。

### 1.5 COA：材料的"体检报告"

**全称**：Certificate of Analysis，分析证书（也叫材质证明/检验报告）。

> **术语歧义提示**：COA 在不同产线可能指不同东西。半导体/材料语境下最常见的是 Certificate of Analysis。**请以你所在产线的内部定义为准。** 本文按此展开，并在末尾给出它与 COC 的区别。

**它是什么**：供应商随批次（lot）提供的**实测数据报告**——不是"我保证符合"，而是"我测了，这是数值"。

| 项 | 内容 |
|---|---|
| 材料批号 | 供应商 lot ID（**这是追溯的源头**） |
| 规格项 | 纯度、金属离子含量、颗粒数、粘度、水分、粒径分布… |
| 实测值 + 方法 | 每个规格项的测量结果 + 测试方法（如 ICP-MS） |
| 判定 | Pass / Fail（对照规格上下限） |

**它与 COC 的区别（很容易混）**：

| | COA（Certificate of Analysis） | COC（Certificate of Conformance） |
|---|---|---|
| 给什么 | **实测数值** + 方法 | **符合性声明**（"符合规格"） |
| 信息量 | 高（可做趋势分析） | 低（只有结论） |
| 用途 | IQC 判定、SPC 入料监控、供应商对比 | 合规存档 |

**对 AI 的价值（常被忽略）**：

COA 是**唯一能提前拿到"上游材料变异"的数据**。如果你的良率突然掉了，而 FDC/SPC 都没报警，**第一个该查的就是近期 COA 里某个规格项有没有漂移**。

**落地要点**：COA 通常是 **PDF/Excel**，格式各供应商不同。**把它结构化成表（材料批号 → 规格项 → 实测值）是很多"良率归因"项目的第一步，也是最脏的一步。**

### 1.6 SPC：用统计判断"这算不算变了"

**全称**：Statistical Process Control，统计过程控制。

**核心思想**（一句话）：**区分"普通原因变异"和"特殊原因变异"。**

- 普通原因（common cause）：工艺本身的固有波动，调它没用，要改工艺；
- 特殊原因（special cause）：某个可归因的事件（设备偏移、材料批次、操作失误），**必须找出来**。

**工具：控制图（Control Chart）**

最常用三种：

| 图 | 适用 | 统计量 |
|---|---|---|
| **X̄-R**（均值-极差） | 子组抽样（如每批测 5 点） | 组均值 + 组内极差 |
| **I-MR**（单值-移动极差） | 单件测量（半导体常见，因为 wafer 内测量点少） | 单值 + 相邻差 |
| **EWMA / CUSUM** | 检测**微小但持续的偏移** | 指数加权 / 累积和 |

**控制限 vs 规格限（这是最常被混淆的一对）**：

| | 控制限（Control Limit） | 规格限（Spec Limit） |
|---|---|---|
| 来源 | **从数据算出来**（±3σ） | **客户/设计定义** |
| 含义 | 过程"正常波动"的范围 | 产品"能否接受"的边界 |
| 超出后 | 过程失控（OOC）→ 查原因 | 产品不合格（OOS）→ 判废/返工 |
| 谁定 | 工艺工程师 | 设计/客户 |

**关键洞察**：**控制限比规格限窄**（正常情况）。如果控制限逼近甚至超过规格限，说明 **Cpk 不够，工艺能力不足**——这是"要改工艺"而不是"要调控制图"的信号。

**能力指标**：

```
Cp  = (USL − LSL) / (6σ_within)      # 潜在能力（不考虑居中）
Cpk = min(USL−μ, μ−LSL) / (3σ_within)  # 实际能力（考虑居中）
Pp/Ppk = 同上，但用 σ_overall           # 长期表现
```

**经验判据**：Cpk ≥ 1.33 是量产门槛，≥ 1.67 是汽车/高可靠场景的常见要求。

**判异规则**：除了"超出 ±3σ"，还有 **Nelson rules（8 条）/ Western Electric rules（4 条）**，用来捕捉"没超限但形态异常"的模式：

- 连续 7 点在中心线同侧（均值偏移）；
- 连续 6 点递增/递减（趋势）；
- 连续 14 点交替上下（系统性振荡）；
- 2/3 点落在 ±2σ 外（接近失控）。

**这 8 条规则是"规则引擎"的经典案例，也是 AI 最容易做出增益的地方**——因为**多条规则同时触发时，人工判断"到底是哪种异常"很费时**（见 4.3）。

### 1.7 FDC：盯着设备的"心电图"

**全称**：Fault Detection and Classification，故障检测与分类。

**它与 SPC 的根本区别（这是全文最重要的一处辨析）**：

| | SPC | FDC |
|---|---|---|
| **监控对象** | **产品质量**（量测结果：膜厚、CD、overlay） | **设备状态**（传感器时序：RF 功率、腔压、气体流量、温度） |
| **数据来源** | 量测机台（metrology） | 设备自身的 trace 数据 |
| **采样节奏** | 批次级 / 每批几个点（**滞后**） | **in-situ，秒级（实时）** |
| **反馈速度** | 加工完 + 量测完才知道（可能几小时） | 加工**过程中**就能发现 |
| **典型异常** | 膜厚偏移、CD 漂移 | 腔体漏气、RF 反射功率异常、气流不稳 |
| **处置** | hold lot、重工 | **中止当前片**（interlock / abort） |

**一句话**：**SPC 是"事后体检"，FDC 是"术中监护"。**

**FDC 的技术栈（三代）**：

| 代际 | 方法 | 特点 | 局限 |
|---|---|---|---|
| **第一代** | 单变量阈值 + 指纹比对（golden trace） | 简单、可解释 | 漏报多；阈值难调；每 recipe 要单独设 |
| **第二代** | 多变量统计（PCA、Hotelling T²、SPE/DModX） | 能捕捉"单个正常、组合异常" | 假设近线性；漂移后要重训 |
| **第三代** | 深度学习（AutoEncoder、LSTM/TCN、对比学习） | 能建模复杂时序模式 | 黑箱；样本不平衡；验证难 |

**FDC 的三个真实难点**：

1. ** nuisance alarm（骚扰告警）**。阈值设太严 → 告警爆炸 → 工程师关掉告警 → 系统形同虚设。这是 FDC 项目失败的最主要原因。
2. **跨机台差异**。同型号机台的 trace 分布也有差异（腔体老化、部件更换）。**"一模一台"是常态**，做全局模型很难。
3. **标签极稀疏**。真实故障几百次里才有一次，**有标签的故障更是少数**。所以 FDC 的 AI 化通常是**无监督异常检测**，而不是分类。

### 1.8 SOP：正常时怎么做

**全称**：Standard Operating Procedure，标准作业程序。

**它的定位**：**"正常路径"的说明书**。包括操作步骤、参数设定、安全注意事项、记录要求。

**在半导体里的特殊要求**：

- **版本受控**：SOP 有版本号，改动要审批（变更管理）；
- **与 recipe 绑定**：SOP 说"用 recipe A 的 2.1 版"，MES 要能校验；
- **培训记录**：谁在什么时候培训过哪一版（审计要求）；
- **现场可得**：工位上要能查到（纸质或电子）。

**对 AI 的价值**：SOP 是**最容易被低估的知识资产**。它包含了大量"工艺专家的隐性知识"（为什么要这样做、什么情况要停）。**做 RAG 问答时，SOP 是最优质的语料**（见 4.6）。

### 1.9 OCAP：异常时怎么做

**全称**：Out of Control Action Plan，失控行动计划。

**它的定位**：**"异常路径"的决策树**——**提前写好的 if-then**。

**典型 OCAP 的内容结构**：

```
触发条件：SPC X̄ 图连续 7 点上升 / Cpk < 1.33 / FDC alarm A-07
  ↓
Step 1：确认数据（是否量测错误？是否录入错误？）
Step 2：立即动作（Hold lot / 停设备 / 通知谁）
Step 3：排查清单（按可能性排序：查设备 → 查材料 → 查操作 → 查环境）
Step 4：判定标准（什么情况放行、什么情况报废、什么情况升级）
Step 5：记录要求（要填哪些字段、附哪些证据）
Step 6：升级路径（多久没解决要找谁）
```

**OCAP 与 SOP 的关系**（这是最容易混的一对）：

| | SOP | OCAP |
|---|---|---|
| 覆盖场景 | **正常** | **异常** |
| 触发 | 按计划执行 | 被事件触发（OOC / alarm） |
| 内容 | 步骤、参数 | **判断、处置、升级** |
| 读者 | 操作员 | 工程师为主 |
| 变更频率 | 低 | 中（每次 8D 后可能更新） |

**一句话**：**SOP 是"怎么干"，OCAP 是"出事了怎么办"。**

**OCAP 是 AI 落地的最佳切入点之一**，原因很实在：**它天然是决策树，而决策树是可以被学习、被检索、被自动匹配的**。而且它的失败代价可控（AI 建议、人确认）。

### 1.10 8D：把一次异常变成不再发生

**全称**：Eight Disciplines，八项纪律（问题解决法）。

**八个步骤**（注意 D0 有时被单列）：

| 步骤 | 名称 | 关键产出 | 常见敷衍做法 |
|---|---|---|---|
| **D0** | 应急反应 | 临时措施 | 跳过 |
| **D1** | 组建团队 | 跨职能小组 | 只拉自己部门 |
| **D2** | 描述问题 | **5W2H + 量化**（多少片、什么时间、哪个腔体） | "良率低了"（不可量化） |
| **D3** | 临时遏制（ICA） | 隔离库存、加严检验 | 只处理在制，忘了已出货 |
| **D4** | 根本原因（RCA） | 5Why + 鱼骨图 + **验证** | 停在"操作员疏忽" |
| **D5** | 永久纠正措施（PCA） | 选方案、评估风险 | 只治标 |
| **D6** | 实施与验证 | 数据证明有效 | 改了就宣布完成 |
| **D7** | 预防再发 | **更新 SOP / OCAP / FMEA / 控制计划** | 忘掉这一步 |
| **D8** | 团队认可与关闭 | 归档、横展到其他产线 | 只关闭不横展 |

**D4 是最容易失败的一步**，三个典型病症：

1. **停在"人为失误"**：这不是根因，是"为什么人会容易犯这个错"的起点（防错设计、界面、培训、疲劳）；
2. **没有验证根因**：找到原因后要能"复现"（把原因加回去，问题重现）或"消除验证"（去掉原因，问题消失）；
3. **单因假设**：实际原因常是多因素叠加（设备微偏 + 材料批次 + 环境湿度），只改一个不够。

**D7 是 AI 最有价值的一步**（很少被这么用）：**把 8D 的结论自动写回 OCAP / FMEA / 控制计划**。这是"组织记忆"的落地方式——见 4.5。

**8D 与 5Why、鱼骨图的关系**：8D 是**框架**，5Why 和鱼骨图是 **D4 里的工具**。不要把它们并列。

### 1.11 DOE：用最少的实验找出参数窗口

**全称**：Design of Experiments，实验设计。

**它解决什么**：工艺有 8 个参数，每个 3 个水平，全试一遍是 `3^8 = 6561` 次实验。**DOE 用统计方法把次数压到几十次，还能分辨主效应和交互效应。**

**四类设计（按用途）**：

| 类型 | 用途 | 实验次数（8 因子为例） | 何时用 |
|---|---|---|---|
| **全因子（Full Factorial）** | 精确估计所有主效应 + 交互 | `2^8 = 256` | 因子少（≤4）、要精细 |
| **部分因子（Fractional Factorial）** | 筛因子（哪些重要） | `2^(8-4) = 16` | **因子多、先做筛选**（最常用） |
| **Plackett-Burman** | 极快速筛（只估主效应） | 12 | 因子很多（>10）、预算极紧 |
| **响应曲面（RSM / CCD / Box-Behnken）** | 找最优点（不是找显著因子） | 20–50 | 已筛出 2–3 个关键因子，要优化 |

**三个必须懂的统计概念**：

| 概念 | 含义 | 工程后果 |
|---|---|---|
| **混杂（Confounding）** | 部分因子设计里，高阶交互与主效应"绑"在一起 | 如果真实存在强交互，会误判主效应 |
| **分辨率（Resolution）** | III / IV / V，越高混杂越少 | RIII 主效应不与主效应混；RIV 主效应不与二阶交互混 |
| **区组（Blocking）** | 把"非研究因子"（如不同批次、不同天）分块 | 不做区组，会把批次差异当成因子效应 |

**踩坑（AI 工程师特别容易犯）**：

- **把 DOE 数据直接喂给模型做拟合**：部分因子设计的数据是"稀疏、有混杂"的，**直接做特征重要性会得到错误的结论**（因为存在 alias）；
- **忽略中心点（center points）**：中心点用来检验"是否存在曲率"，没有它就无法判断该不该上 RSM；
- **随机化（randomization）没做**：不随机化，时间漂移会混进因子效应。

**AI 与 DOE 的结合点**：**贝叶斯优化 / 主动学习**。传统 DOE 是"一次性设计"，贝叶斯优化是"序贯设计"——每做一批实验，用结果更新代理模型，再选下一批最有信息量的点。**这在实验成本极高（一片 wafer 几千美元）的场景下价值很大**。

### 1.12 APQP：产品导入期的"质量总纲"

**全称**：Advanced Product Quality Planning，先期质量策划。

**出身**：AIAG（美国汽车工业行动集团）的质量框架，配合 IATF 16949。**半导体做车规（AEC-Q100/Q101）时几乎必然被客户要求。**

**五个阶段与交付物**：

| 阶段 | 名称 | 关键交付物 |
|---|---|---|
| **① 策划** | Plan and Define Program | 客户需求、可靠性目标、**初始 BOM/流程图** |
| **② 产品设计** | Product Design & Development | **DFMEA**、设计验证计划（DVP&R）、图纸 |
| **③ 过程设计** | Process Design & Development | **PFMEA**、**控制计划（Control Plan）**、MSA、过程流程图 |
| **④ 产品与过程确认** | Product & Process Validation | **PPAP** 提交、试生产、能力验证（Cpk） |
| **⑤ 反馈与纠正** | Feedback, Assessment & Corrective Action | 量产监控、**8D**、持续改进 |

**两个必须知道的缩写**：

| 缩写 | 全称 | 是什么 |
|---|---|---|
| **PFMEA** | Process FMEA | 过程失效模式分析：列出每个工序可能的失效、严重度(S)/频度(O)/探测度(D)，算 RPN |
| **PPAP** | Production Part Approval Process | 生产件批准程序：向客户提交的一整套证据包（通常 18 项） |

**APQP 对 AI 落地的决定性作用（这是全文最关键的一条）**：

> **APQP 阶段 ③ 产出的"控制计划"，定义了哪些参数进 SPC、哪些进 FDC、采样频率多少、失控时执行哪个 OCAP。**

换句话说：

```
APQP（策划）→ 控制计划（决策）→ SPC / FDC 的监控项（执行）
                                    ↓ 异常
                                 OCAP（处置）
                                    ↓ 根因
                                  8D（闭环）
                                    ↓ D7
                              更新 SOP / FMEA / 控制计划（回到 APQP）
```

**这就是"质量闭环"的完整链路。** 而 AI 只要碰"监控项"或"判定规则"，就动到了控制计划——**而控制计划是客户批准过的**（见 5.1）。

### 1.13 Dify：AI 应用层，不属于产线栈

**它是什么**：开源的 LLM 应用开发平台（LLMOps）。核心能力：

| 能力 | 内容 |
|---|---|
| **可视化编排** | 拖拽式 workflow（LLM / 检索 / 条件分支 / 代码节点） |
| **RAG pipeline** | 文档切分、向量化、检索、重排 |
| **Agent** | 工具调用、多步规划 |
| **模型管理** | 多模型接入、切换、参数配置 |
| **可观测** | 日志、trace、成本统计 |
| **发布** | API / 内嵌页面 |

**它和前面 12 个词的关系**：**没有直接关系。** 它不采集设备数据，不做 SPC，不控设备。

**它真正的用途（在半导体场景里）**：

| 场景 | 用 Dify 做什么 | 关键前提 |
|---|---|---|
| **SOP / OCAP 问答助手** | 把 SOP、OCAP、设备手册、历史 8D 灌进 RAG，让工程师用自然语言查 | **文档要结构化、版本要标注** |
| **8D 报告起草** | 输入异常描述，生成 D8 初稿框架 | 只能起草，不能定稿 |
| **良率异常初筛** | 结合规则引擎输出 + LLM 生成"可能原因清单" | **必须有确定性工具做事实计算，LLM 只做归纳** |
| **培训与考试** | 基于 SOP 生成问答对 | 内容正确性要人工校验 |

**必须提醒的三点（这是"AI 应用层"最容易翻车的地方）**：

1. **不要把 LLM 当计算器**。良率、Cpk、偏移量必须由确定性代码算，LLM 只解释结果。**在工业场景，一个算错的数字比一个答不出的问题严重得多。**
2. **RAG 的召回质量决定一切**。如果 SOP 是扫描版 PDF、没有版本号、段落切得乱七八糟，RAG 会给出"看起来对但引用了过期版本"的答案。**这是最危险的失败模式**（因为答案读起来很合理）。
3. **不要把 Dify 放进控制回路**。它适合"人问它答"，不适合"它判断然后设备动作"。**任何影响 lot 处置的决策，不能由 LLM 直接输出。**

## 2. 三条数据流：把术语串成链

术语背下来没用，**要能画出"数据从哪来、经过谁、到哪去"**。半导体产线其实只有三条流，它们在不同位置汇合。

### 2.1 流一：设备信号流（秒级，实时）

```
设备传感器 (L0)
   ↓ 模拟/数字信号
设备控制器 (L1) —— 采样、闭环
   ↓ SECS/GEM (E5/E30)
EAP (L2) —— 协议转换、Trace 采集、时间戳
   ↓ 消息队列 / 数据库
FDC (L2-L3) —— 多变量模型、阈值判定
   ↓ alarm
MES (L3) —— Hold lot / 停设备
   ↓
OCAP —— 工程师按预案处置
```

**特点**：**高频、实时、以设备为中心**。数据量最大（一台设备一天几个 GB 的 trace 很常见）。

**AI 切入点**：异常检测、虚拟量测、漂移预警。**难点是标注稀疏 + 跨机台差异**。

### 2.2 流二：质量测量流（批次级，滞后）

```
加工完成
   ↓
量测机台（metrology：膜厚/CD/overlay/defect review）
   ↓ 测量结果（每批 5-25 个点）
MES —— 与 lot 绑定，写谱系
   ↓
SPC (L3) —— 控制图、Cpk、Nelson rules
   ↓ OOC
OCAP —— 判定：放行 / 重工 / 报废 / 升级
   ↓ 若根因不明
8D —— D2 描述 → D4 根因 → D5-D6 措施 → D7 更新标准
   ↓
更新 SOP / 控制计划 / FMEA
```

**特点**：**低频、滞后、以产品为中心**。数据量小（但每条都关键）。

**AI 切入点**：虚拟量测（用设备 trace 预测量测结果，**把滞后变成实时**）、Cpk 预测、OOC 归因。

### 2.3 流三：缺陷图像流（片级，准实时）

```
AOI (L1) —— 成像、差分、出候选
   ↓ 候选 patch + 坐标
ADC (L1-L3) —— 分类（规则 or 模型）
   ↓ bin code
良率分析系统（Yield Management）—— 缺陷 Pareto、wafer map 聚类
   ↓ 发现系统性缺陷
8D / 根因分析 —— 查设备、查材料（COA）、查工艺
   ↓
更新检测配方 / 控制计划
```

**特点**：**中频、大文件（图像）、以缺陷为中心**。

**AI 切入点**：**误报过滤（最高 ROI）**、缺陷分类、wafer map 图案识别。

### 2.4 三流如何汇合：一次真实的异常排查

假设良率突然掉了 2%。**三流在这里汇合**：

```
1. 良率系统发现某产品良率下降（流三：缺陷统计）
   ↓
2. 查 wafer map：缺陷集中在 wafer 边缘（图案识别）
   ↓
3. 查谱系（MES）：这批 wafer 都经过了 3 号刻蚀机的 B 腔
   ↓
4. 查 FDC（流一）：B 腔的 RF 反射功率在过去 3 天有缓慢上升
   ↓
5. 查 SPC（流二）：CD 量测的均值有 0.8nm 偏移，但还在控制限内（未触发 OOC）
   ↓
6. 查 COA：同期换了一批新的刻蚀气体，COA 显示水分含量在规格内但偏高
   ↓
7. 结论：气体水分 + 腔体老化 叠加 → RF 匹配变差 → 边缘刻蚀速率不均
   ↓
8. 8D：D5 换腔体部件 + 收紧气体 COA 的水分内控线
   ↓
9. D7：把"RF 反射功率的斜率"加入 FDC 监控项（原先只监控绝对值）
       → 更新控制计划
```

**这个案例说明了三件事**：

1. **单看任何一条流都找不到根因**——SPC 没报警（在限内），FDC 没报警（绝对值正常），只有"跨流关联"才发现；
2. **AI 的机会在"跨流关联"**，而不是"把某一个模型做准"；
3. **最终动作是"改控制计划"**——这解释了为什么 AI 落地的最大阻力在变更管理（见 5.1）。

## 3. 上下游依赖关系与易混淆对照

### 3.1 依赖图（谁决定谁）

```
[APQP] ──产出──> [控制计划 Control Plan]
                        │
                        │ 定义：监控哪些参数 / 采样频率 / 失控执行哪个 OCAP
                        ↓
        ┌───────────────┴───────────────┐
        ↓                               ↓
[SPC] 产品质量侧                    [FDC] 设备状态侧
控制图 / Cpk / Nelson rules         Trace 多变量 / 阈值 / 模型
        ↓                               ↓
   OOC / OOS                          alarm
        └───────────────┬───────────────┘
                        ↓
                  [OCAP] 按预案处置
                  放行 / 重工 / 报废 / 升级
                        ↓ 若根因不明
                   [8D] D1..D8
                        ↓ D7 预防再发
        更新 SOP / PFMEA / 控制计划 ──> 回到 [APQP]（下一轮）

注：[DOE] 独立于这条主链，它产出"工艺窗口"（规格限与中心值），
    是 [控制计划] 的输入之一。
```

**三条硬依赖，记这三条就够**：

| 依赖 | 含义 | 违背的后果 |
|---|---|---|
| **APQP → 控制计划 → SPC/FDC** | 监控什么、怎么监控，是策划阶段定的 | 如果 AI 想加监控项，必须走变更 |
| **DOE → 规格限/中心值** | 规格不是拍脑袋，是实验定出来的 | 用错规格限，Cpk 算出来是假的 |
| **8D 的 D7 → 标准更新** | 闭环的终点是"标准变了" | 不改标准，同类问题必然复发 |

### 3.2 七对最容易混淆的术语

| 对 | 区别（一句话） | 混错的后果 |
|---|---|---|
| **SPC vs FDC** | 事后量产品 vs 术中看设备；批次级 vs 秒级 | 用 SPC 的数据做实时控制（滞后几小时）；用 FDC 的数据做能力分析（trace 不是产品特性） |
| **OCAP vs SOP** | 异常时怎么办 vs 正常时怎么做 | 出事了查 SOP，查不到处置方案 |
| **AOI vs ADC** | 找"哪里有异常" vs 判"这是什么异常" | 以为上了 AOI 就有了分类能力，实际还要复判 |
| **控制限 vs 规格限** | 数据算的 vs 客户定的 | 用规格限画控制图 → 永远不报警（限太宽） |
| **8D vs 5Why** | 框架 vs 工具（5Why 在 D4 里） | 把 5Why 当完整方法论，做完没有防再发 |
| **APQP vs PPAP** | 过程（5 阶段） vs 交付物（证据包） | 以为交了 PPAP 就完成 APQP |
| **COA vs COC** | 给数据 vs 给声明 | 只留 COC，出问题时无法做趋势分析 |

### 3.3 四组"看起来相关但无关"的术语

这一组更隐蔽，因为**它们在中文字面上很像，但在系统里完全没有关系**：

| 组 | 为什么容易混 | 实际关系 |
|---|---|---|
| **MES vs EAP** | 都"管设备" | MES 管工单与谱系（L3），EAP 管通信与采集（L2）。**MES 不知道 SECS 消息长什么样，EAP 不知道 lot 的优先级** |
| **FDC vs 良率分析** | 都在"发现异常" | FDC 看**实时设备信号**，良率分析看**累积的缺陷/量测统计**。**FDC 报警不等于良率会掉**（反之亦然） |
| **ADC vs 缺陷检测** | 都叫"检测" | 检测（inspection）是"发现异常像素"，分类（ADC）是"给它命名"。**先检测后分类，是两个工序** |
| **Dify vs MES** | 都"有工作流" | Dify 的 workflow 是**LLM 编排**（prompt→检索→生成），MES 的 workflow 是**物理批次流转**。二者没有替代关系 |

## 4. 六个 AI 落地机会（按 ROI 排序）

排序依据不是"技术先进性"，而是 **ROI = 收益 / （技术风险 × 变更成本）**。

### 4.1 机会一：AOI 误报过滤（ROI 最高）

**为什么排第一**：

| 维度 | 评估 |
|---|---|
| 痛点明确 | 复判是人力瓶颈，30%–70% 的候选是误报（范围性表述） |
| 数据现成 | AOI 已经在存缺陷图像 + 坐标 + 设备参数，**不需要新增采集** |
| 标签现成 | 复判结果（工程师判 OK/NG）就是标签，**已经存在系统里** |
| 评估明确 | "过滤掉多少误报 + 漏掉多少真缺陷"是一个清晰的权衡曲线 |
| **失败成本低** | **AI 只做"减法"（把明显是误报的挑出来给人快速过），最坏情况是多留几条给人看** |
| 变更阻力小 | 不改控制计划，只改"人看多少条" |

**技术要点**：

1. **输入不只是图像**：缺陷的坐标、尺寸、长宽比、灰度统计、以及**该 die 的工艺参数**都是有效特征；
2. **不要做二分类，做排序**。输出"这是误报的概率"，然后按阈值过滤——**这样工程上可以调"放过多少"，而不是被迫在某个点上取舍**；
3. **按缺陷类型分组评估**。整体误报率降低 50%，但某类致命缺陷的漏检上升——**这是不可接受的，必须分组看**；
4. **必须能"拒绝判断"**。低置信度的样本直接送人工，**不要强判**。

**落地形态**：AI 前置过滤 → 人工快速确认（从"逐条判"变成"批量确认"）→ 真缺陷进 ADC。

### 4.2 机会二：ADC 缺陷分类

**为什么排第二**：ROI 高，但**比误报过滤多两个风险**（类别不平衡 + 类别体系要映射）。

**技术要点**：

1. **bin code 映射是第一步，不是最后一步**。先和客户/工艺确认"你说的 bin 3 到底指什么"，再设计分类头；
2. **用层次分类而非平铺分类**：先分大类（particle / scratch / pattern / void），再分细类。**这样新类别出现时可以只改子分类器**；
3. **少样本类用度量学习**（prototypical network / triplet），因为致命缺陷样本天然少；
4. **必须报混淆矩阵 + per-class recall**，不能只报 accuracy；
5. **模型不确定时输出"Unknown"**，让工程师归类——**这比强行归类更有价值**（Unknown 的样本是下一轮标注的素材）。

### 4.3 机会三：FDC 异常检测（含"骚扰告警"治理）

**注意：这里的 ROI 不在"发现新故障"，而在"减少无效告警"。**

**为什么**：大多数 fab 已经有 FDC 系统，且**工程师对告警的信任度已经被"告警爆炸"摧毁**。你再加一个模型说"我发现了新异常"，大概率被忽略。

**真正有价值的三个方向**：

| 方向 | 做法 | 收益 |
|---|---|---|
| **告警去重/聚合** | 把同一根因触发的 20 条告警合并成 1 条 | 工程师处理量降 80% |
| **自适应阈值** | 用历史数据自动算每台机台每变量的合理范围（而非全局固定阈值） | 减少 nuisance alarm |
| **告警优先级排序** | 基于"历史上有多少告警最终导致 hold/报废"给告警打分 | 让工程师先看重要的 |

**技术要点**：

1. **优先做"每机台一模型"而不是"全局模型"**。跨机台差异太大，全局模型在多数机台上都不准；
2. **用无监督 + 少量标签**（PU learning / 半监督）。异常样本极少，纯监督不可行；
3. **可解释性是硬要求**（见 5.2）：**必须给出"是哪个变量、在什么时间段、偏离了多少"**。只说"异常分数 0.87"的模型不会被采纳。

### 4.4 机会四：虚拟量测（VM）

**机制**：用**设备 trace 数据**预测**量测结果**（膜厚、CD、overlay）。

```
真实量测：加工 → 送去量测机台 → 2 小时后拿到结果 → SPC 判 → 晚了
虚拟量测：加工 → 用 trace 预测 → 秒级拿到预测值 → 提前发现异常
```

**为什么价值大**：

- **量测是瓶颈**（量测机台贵、排队久、有些是抽检）；
- **VM 能做到"片片全检"**（真实量测只能抽检）；
- **可以提前触发 hold**（不用等量测完才发现问题）。

**技术要点**：

1. **VM 的精度要求极高**。量测本身有噪声（repeatability），**VM 的误差必须显著小于规格带宽**（经验：VM 误差 < 10% 规格带宽才有用）；
2. **必须做"适用域检测"（applicability domain）**：当 trace 落在训练分布外时（如新 recipe、设备大修后），VM 要**拒绝输出**，而不是给一个错的预测；
3. **VM 不能替代量测**（客户审核不认），只能做"预警"。**这一点必须在项目立项时说清楚，否则验收时会被推翻。**

### 4.5 机会五：根因分析与 8D 加速

**这是"跨流关联"的典型场景**（见 2.4 的案例）。

**三个层次**：

| 层次 | 做法 | 难度 | 价值 |
|---|---|---|---|
| **L1 检索** | 从历史 8D / OCAP 里找"类似问题怎么解决的" | 低（RAG） | 中（省查资料时间） |
| **L2 关联** | 把良率下降与 FDC/SPC/COA/谱系做统计关联，输出候选原因排序 | 中 | **高** |
| **L3 因果** | 用因果图/干预实验确认根因 | 高 | 最高（但通常要人做实验） |

**建议从 L1 + L2 做起**，L3 交给工艺工程师（他们要的是"候选清单"，不是"结论"）。

**L2 的关键工程点**：

- **必须能 join 谱系**（MES）：没有"这批 wafer 经过了哪些机台/腔体"，就无法做关联；
- **必须做多重比较校正**：你同时检验 200 个变量，α=0.05 会有 10 个假阳性（见《开放域问答评测》那篇里的统计部分）；
- **输出必须是"排序 + 证据"，不是"结论"**。工程师要能自己判断。

### 4.6 机会六：知识助手（SOP/OCAP 问答）

**这就是 Dify 这类平台的用武之地**。

**做对了的三条**：

1. **只答"文档里有的"**，答不出就说没有（**不要让它推理**）；
2. **必须给出版本 + 段落引用**（"根据 SOP-ETCH-021 v3.2 第 4.3 节"）——**没有版本号的回答在审计时等于零**；
3. **答案是"指向原文"，不是"总结"**。工程师要的是原文，不是 LLM 的转述。

**做错了的三种（都很常见）**：

| 错误 | 后果 |
|---|---|
| 让它算 Cpk / 良率 | 算错（LLM 不擅长数值计算） |
| 混入网页/通用语料 | 给出"行业通行做法"而非"本厂规定"，**这是最危险的** |
| 不做版本管理 | 引用过期 SOP，导致操作错误 |

## 5. 工业场景的三个硬约束

### 5.1 合规：模型上线 = 工艺变更

这是 AI 落地半导体最大的、也是最容易被低估的障碍。

**核心逻辑链**：

```
AI 模型影响了"某个 lot 是否放行"
  ↓
这改变了"过程的判定规则"
  ↓
在 IATF 16949 / 客户审核体系里，这是"过程变更"
  ↓
必须走变更管理：影响评估 → 验证 → 客户批准（车规场景）
  ↓
（在 APQP 体系里，还要更新控制计划）
```

**这意味着**：

| 你以为在做 | 实际在做 |
|---|---|
| "上线一个模型" | "发起一次工艺变更" |
| "迭代模型版本" | "重复一次变更流程" |
| "模型效果提升 3 个点" | "需要重新提交验证证据" |

**三条应对策略**：

1. **把 AI 放在"建议"位置，不放"决策"位置**。人签字，AI 只是提供输入——**这样不构成过程变更**；
2. **先做"减法"**（减少复判量、减少告警数），**后做"加法"**（新增检出、自动处置）。减法的变更风险远小于加法；
3. **从"辅助工具"立项，不要从"AI 决策系统"立项**。前者走 IT 变更流程，后者走工艺变更流程，**周期差 5–10 倍**。

**其他合规项**：

- **数据完整性**：谁改了模型、什么时候、基于什么数据（类似 ALCOA+ 原则）；
- **可追溯**：任何一个判定，要能回溯到"当时用的是哪个模型版本 + 哪批训练数据"；
- **客户特定要求**：车规客户（AEC-Q100）通常要求"任何影响产品特性的变更都要通知"。

### 5.2 可解释：工程师要能"为这个判断负责"

**为什么可解释在工业里是刚需（而不是"nice to have"）**：

工程师在 8D 报告上签字，意味着"我愿意为这个结论负责"。**如果他无法向客户解释"为什么模型这么判"，他就不会签。**

具体需要什么：

| 需求 | 具体形式 | 不满足的后果 |
|---|---|---|
| **定位到变量** | "腔体压力在 t=120s 偏离基线 3.2σ" | 只说"异常分数高"，无法排查 |
| **定位到时间** | 精确到秒的时间窗 | 无法回看当时发生了什么 |
| **定位到样本** | 哪几片/哪几个 die | 无法界定 hold 范围 |
| **可复现** | 同样输入 → 同样输出（无随机性） | 无法在评审时复现 |
| **可对比** | 与"正常时的基线"对比 | 无法判断"偏了多少" |

**一个实操建议**：**把"解释"当成产品的第一功能，而不是附加功能。**

具体做法：

- 模型的输出**不是**一个分数，而是"分数 + top-3 贡献变量 + 时间窗 + 对比基线"；
- 界面上**同时展示原始 trace 曲线**（标注异常区间），而不只是结论；
- 保留**每次判定的快照**（输入数据 + 模型版本 + 输出），供事后审计。

### 5.3 停机风险：两类错误的代价不对称

**这是工业 AI 与互联网 AI 最本质的差异**。

| 错误类型 | 后果 | 代价量级 |
|---|---|---|
| **误报（False Positive）** | 停机检查 → 产能损失 + 该批可能报废（热预算） | 中（可承受，但累积起来很大） |
| **漏报（False Negative）** | 批量不良流出 → 客户投诉 + 召回 + 信誉 | **极高（可能数百万美元 + 客户关系）** |

**代价不对称的直接后果**：

1. **阈值必须偏保守**（宁可多报）。这意味着你做的"高精度模型"在业务上会被调到"高召回"——**你的 AUC 提升可能根本体现不出来**；
2. **评估指标要和业务对齐**：不要报 accuracy / F1，要报 **"在给定漏检率上限下，误报率能降到多少"**；
3. **必须区分"可停机"和"不可停机"的告警**。有些工序（如炉管、湿法）停机代价极高（要重新升温/换液），这类工序的模型必须更保守。

**一个实操框架**：

```
1. 和工艺确认"可接受的漏检率"（如 < 0.1%）
2. 在这个约束下，最大化"误报过滤率"
3. 报"过滤率 @ 漏检率 0.1%" 这个数字，而不是 AUC
4. 给出"如果阈值再放宽，过滤率能到多少，但漏检会升到多少"的曲线
```

**这条曲线（类似 DET 曲线）比任何单一指标都有说服力**，因为它把决策权交给了工艺工程师。

### 5.4 第四个约束（常被漏掉）：数据可得性

| 约束 | 表现 | 应对 |
|---|---|---|
| **标注成本** | 缺陷标注需要工程师 + SEM 复检，一条几美元到几十美元 | 主动学习（只标最有价值的样本） |
| **样本不平衡** | 致命缺陷 < 0.1% | 用 anomaly detection 而非 classification |
| **数据孤岛** | 设备数据在 EAP 库、量测在 SPC 库、谱系在 MES 库 | 先做数据打通（这往往是项目 60% 的工作量） |
| **历史数据不可用** | 老设备没开 Trace；系统升级导致格式变化 | 项目前先做数据可用性评估 |
| **隐私/出口管制** | 有些 fab 不允许数据出内网 | 必须支持本地部署（这也是 Dify 开源版的价值之一） |

## 6. 落地路径建议

### 6.1 一个 12 个月的现实路径

```
M1–M2：数据可达性评估（不要跳过）
  □ 目标工序有没有 Trace？采样率？变量字典有没有？
  □ 量测数据能不能按 lot 对齐？
  □ MES 谱系能不能 join？
  □ 历史标签（复判结果/8D）有多少条？
  → 产出：可行性报告。这里的结论经常是"数据不够，先做数据治理"

M3–M5：AOI 误报过滤（第一个 ROI）
  □ 不改控制计划、不做自动决策，只做"人看多少条"
  □ 评估指标：过滤率 @ 漏检率 0.1%
  □ 上线形态：AI 前置 + 人工确认

M6–M8：FDC 告警治理
  □ 先把现有告警的"有效告警率"算出来（通常 < 20%）
  □ 做去重/聚合 + 自适应阈值
  □ 指标：工程师日均处理告警数、有效告警占比

M9–M12：跨流关联（根因候选）
  □ 打通设备 + 量测 + 谱系
  □ 输出"候选原因排序 + 证据"
  □ 与 8D 流程结合，衡量"平均结案时间"是否缩短
```

**为什么这个顺序**：

| 阶段 | 变更风险 | 数据要求 | 收益可见性 |
|---|---|---|---|
| AOI 误报 | 低（不改判定） | 低（数据现成） | 高（人力节省可量化） |
| FDC 治理 | 低（减少告警不是增加） | 中 | 中 |
| 跨流关联 | 中（影响排查流程） | **高**（要打通三库） | 高但慢 |

### 6.2 三个"不要"

| 不要 | 原因 |
|---|---|
| **不要一上来做"全自动判定"** | 变更流程走不完，且一次误判就会失去信任 |
| **不要用通用异常检测算法（Isolation Forest / AutoEncoder 直接套）** | 半导体 trace 有强周期性、多阶段（step）、变量间强相关，通用方法会产生海量误报 |
| **不要只和 IT 部门对接** | 工艺工程师才是最终用户和签字人，他们的需求（可解释、可复现）决定了方案形态 |

### 6.3 一句话判断项目能不能做

**在立项前问三个问题**：

1. **"如果这个模型判错了，谁承担后果、怎么回滚？"**——答不出来，说明还没到能落地的阶段；
2. **"这个判定要不要写进控制计划/OCAP？"**——要写，就是工艺变更，周期 ×5；
3. **"工艺工程师愿意用一个月，还是只是评审时点头？"**——只点头的，上线三个月就会被弃用。

## 7. 小结

1. **学这些术语的关键是"串成链"，不是背定义。** 三条流（设备信号 / 质量测量 / 缺陷图像）在不同位置汇合，**AI 的价值主要在"跨流关联"，而不是"把单点模型做准"。**
2. **SPC vs FDC 是全文最重要的一处辨析**：SPC 监控**产品质量**（批次级、滞后），FDC 监控**设备状态**（秒级、实时）。**用 SPC 做实时控制会滞后几小时；用 FDC 数据做能力分析是概念错误。**
3. **控制限 ≠ 规格限。** 控制限从数据算（±3σ），规格限由客户/设计定。**用规格限画控制图，永远不报警。**
4. **OCAP vs SOP**：OCAP 是"异常时怎么办"的决策树，SOP 是"正常时怎么做"的说明书。**OCAP 天然适合被检索、被学习，是 AI 最好的切入点之一。**
5. **APQP 决定了一切**：它的阶段③产出"控制计划"，**控制计划定义了哪些参数进 SPC、哪些进 FDC、失控执行哪个 OCAP**。这就是为什么"AI 想加一个监控项"要走变更流程。
6. **8D 的 D7 是最容易被跳过、也最值钱的一步**：把结论写回 SOP / FMEA / 控制计划。**不改标准，同类问题必然复发。AI 在这里的价值是"自动起草标准更新"，而不是"自动找根因"。**
7. **AOI 与 ADC 是两个工序**：AOI 找"哪里有异常"，ADC 判"这是什么异常"。AOI 的痛点是**30%–70% 的误报**（范围性表述），这直接决定了"误报过滤"是 ROI 最高的 AI 机会。
8. **COA 是被低估的数据源**：它是唯一能提前拿到"上游材料变异"的数据。**良率突然掉了而 FDC/SPC 都没报警时，第一个该查 COA。**
9. **Dify 不属于产线栈**。它是 LLM 应用层工具，适合做 SOP/OCAP 问答、8D 起草。**三个红线：不当计算器、必须有版本引用、不进控制回路。**
10. **合规的本质是"模型上线 = 工艺变更"。** 三条应对：放"建议"位不放"决策"位、先做减法后做加法、从"辅助工具"立项而不是"AI 决策系统"。
11. **可解释不是加分项，是入场券。** 工程师要为结论签字。最小可接受形式：**定位到变量 + 时间窗 + 对比基线 + 可复现**。
12. **误报和漏报的代价严重不对称**（漏报可能是数百万美元 + 客户关系）。所以**不要报 AUC/F1，要报"过滤率 @ 漏检率约束"的曲线**——把决策权交给工艺工程师。
13. **落地顺序：AOI 误报 → FDC 告警治理 → 跨流关联。** 前两步"只减不增"，变更风险低；第三步需要打通三库，往往占项目 60% 的工作量。

如果只留一句：**在半导体产线，AI 的技术难度不是主要矛盾——把模型放在"建议位"而不是"决策位"、把指标说成"过滤率@漏检率"而不是 AUC、把解释做成一等功能而不是附加功能，这三件事决定了方案能不能活过第一次评审。**
