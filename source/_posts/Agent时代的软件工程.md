# 一、导语

过去三十年，软件基础设施只有一个隐含目标：**让人用得顺手**。

- 文档是给人读的：有章节、有比喻、有截图、有"注意"和"提示"；
- 界面是给人点的：有按钮、有表单、有加载动画、有错误提示；
- 数据是给人看的：有报表、有仪表盘、有红黄绿灯。

这些设计共享一个前提：**人是那个"填缝"的角色**。文档没写清的，人靠经验补；界面没提示的，人点两下就懂了；报表有歧义的，人打电话问一句。

Agent 没有这个能力。**它不填缝，它填幻觉。**

于是出现了一个正在发生的倒转：**同一个系统，需要同时服务两类消费者，而这两类消费者的最优形态几乎相反。**

| | 给人用 | 给 Agent 用 |
|---|---|---|
| 文档 | 叙述、举例、循序渐进 | 结构化规约、schema、边界条件 |
| 接口 | 图形界面、按钮、向导 | 类型化工具、显式参数、明确错误码 |
| 数据 | 报表、图表、汇总 | 可查询接口、字段元数据、口径说明 |
| 出错 | 友好提示"请稍后重试" | `{"code": "RATE_LIMITED", "retryable": true, "retry_after_ms": 2000}` |
| 核心目标 | **降低认知负荷** | **消除歧义** |

一句话概括这个倒转：**为人的设计在"容错"，为 Agent 的设计在"防错"。** 因为人会宽容含糊，Agent 会把含糊当成自由发挥的空间。

这篇文章想做的，是把"Agent 时代的软件工程"从口号变成可操作的判断——按需求、设计、开发、测试、运维五段拆开，说明每一段具体变了什么；然后在最后专门写一节**这个变化在哪里被夸大了**，因为那一节比前面五节都重要。

# 二、核心命题

基础设施的服务对象发生了倒转，先看三个最基础的基础设施，它们各自正在裂成两个版本。

**① 文档：从"叙述"到"规约"**

| | 给人看（现状） | 给 Agent 看（需要的） |
|---|---|---|
| 形态 | 教程、指南、FAQ | 结构化规约 + schema + 示例 |
| 顺序 | 由浅入深 | 由"必填项"到"可选" |
| 边界 | 常省略（"一般情况"） | 必须穷举（哪些情况不支持） |
| 举例 | 一个完整例子 | 正例 + **反例**（这个不行，因为……） |
| 版本 | 更新公告 | 版本号 + 变更点 + 兼容性说明 |

**为什么必须做这个转换**：人类读文档时会自动补齐"一般情况"之外的部分——我们知道"这个 API 大概也能处理空数组吧，试一下"。Agent 不会试，它会假设，然后给你一个跑得通但语义错的实现。

**反例**：文档写"支持批量导入"。人类会问"多大算批量、超了怎么办"；Agent 会直接按 1 万条写，然后在 10 万条时 OOM。**"支持批量导入"这七个字，对人是线索，对 Agent 是陷阱。**

**② 接口：从"按钮"到"工具"**

这一层的变化已经有事实上的标准了：**MCP（Model Context Protocol）**——2025 年底由 Anthropic 提出，之后被主流工具链广泛采纳，做的就是把"能调用的能力"标准化成 Agent 可读的形式。

MCP 解决的正是"消灭歧义"这个问题，它的关键设计点值得对照：

| 设计点 | 对应的问题 |
|---|---|
| 工具名 + 自然语言描述 | Agent 怎么知道"什么时候该用这个工具" |
| 参数 JSON Schema | 类型、必填、枚举——**不给自由发挥的空间** |
| 返回结构化结果 | 让 Agent 能判断"成功了没有" |
| 错误码而非错误文本 | 让 Agent 能判断"该重试还是该放弃" |
| 能力声明（capabilities） | 让 Agent 能自己发现"你能做什么" |

**注意最后一条的重要性**：这叫**可发现性**。人说"这个系统能干什么"，是靠人翻菜单、看文档、问同事。Agent 需要的是：**不用问，自己就能查出一份能力清单**。

> 一个判断标准：**如果一项能力无法被机器列出清单，它就不具备"Agent 可用性"。**

**③ 数据：从"报表"到"可查询 + 可解释"**

| | 给人看 | 给 Agent 用 |
|---|---|---|
| 形态 | 仪表盘、日报 | 查询接口 + 字段元数据 |
| 粒度 | 汇总后 | 明细可下钻 |
| 口径 | 写在脚注 | 写在字段定义里（含/不含税、时间边界） |
| 异常值 | 标红让人判断 | 显式标记 + 原因码 |

这一层我在《工业多模态知识库的七道工序》那篇里展开过，核心原则是：**索引"怎么查"，不索引"查到的结果"**。这里只强调一点：**口径必须机器可读**。

一个具体例子：报表上写"金额 90 万"，人看到会问"含税吗"，Agent 不会问，它会算。**如果口径不在数据里，Agent 就会用错口径，而且错得很自信。**

什么样的东西算"Agent 友好"，主要看一下三点：

| 标准 | 检验问题 | 不合格的表现 |
|---|---|---|
| **可发现性** | Agent 能不能自己列出一份"我能做什么"的清单？ | 能力藏在菜单/文档里，需要人介绍 |
| **可验证性** | 调用后，Agent 能不能判断"成功/失败/部分成功"？ | 只返回一段自然语言描述 |
| **幂等性** | 同样的调用重复两次，结果一样吗？ | 会重复下单、重复扣款、重复发通知 |

**第三条最容易被忽略，但后果最严重**。Agent 的重试是常态（超时重试、验证失败重试、多 Agent 并行），如果接口不幂等，**Agent 越努力，事故越大**。

# 三、需求：从"用户故事"到"能力契约"

## 3.1 传统需求文档的三个隐含读者

一份典型的用户故事：

> 作为采购员，我希望能够提交采购申请，以便启动审批流程。

这句话对人类开发者足够，因为开发和测试会在实现时自动补齐：

- 金额上限多少？→ 去问产品；
- 审批不通过能不能改？→ 按惯例做成"可修改重新提交"；
- 附件支持什么格式？→ 按经验支持常见格式。

**这些"自动补齐"，本质是把需求文档的空白用组织默契填上了。** Agent 没有组织默契。

## 3.2 能力契约：需求文档的新形态

给 Agent 的需求，必须写成**可以被判定对错**的形式：

| 要素 | 传统写法 | 契约写法 |
|---|---|---|
| 输入 | "采购申请" | 字段清单 + 类型 + 必填 + 枚举 + 边界（金额 > 0 且 ≤ 1e8，两位小数） |
| 前置条件 | 常省略 | 显式列出（申请人状态为"在职"、预算余额充足） |
| 后置条件 | "提交成功" | 可断言的状态（生成申请单号、状态 = PENDING_APPROVAL、通知已入队） |
| 例外 | "异常情况处理" | 穷举 + 每个例外的期望行为（余额不足 → 拒绝，不创建单据） |
| 不做的事 | 常省略 | **显式声明**（不支持撤销、不支持跨年度） |

**第五行是新增的，也是最容易被漏掉的。** 人类开发者知道"没人要求我做撤销，那就不做"；Agent 会在某个边界上"顺手"实现了半成品撤销，然后成为一个谁都不敢碰的隐藏行为。

> **原则：给 Agent 的需求，"不做什么"和"做什么"同样重要。**

## 3.3 一个完整例子：把一句"人话需求"改写成能力契约

抽象讲不如改一遍。取一条最普通的业务规则：

> **"采购申请金额超过 80 万要走招标。"**

这句话给人类开发者，能干活——他会去问三个问题，然后按答案实现。给 Agent，它会**直接实现**，而且实现得看起来完全合理。

**第一步：先看这句话里藏了多少个未定义项**

| 未定义项 | 可能是 | 错一个的后果 |
|---|---|---|
| 80 万**含税还是不含税** | 含税/不含税 | 边界附近全错 |
| **单次还是累计** | 单笔/同供应商年度累计 | 拆分规避查不出来 |
| **等于 80 万**算不算 | $>$ 还是 $\geq$ | 恰好 80 万的项目走错流程 |
| 谁来判断 | 系统/人工 | 责任不清 |
| 不满足时怎么办 | 报错/降级/阻断 | 流程卡死或放行 |

**这五个未定义项，就是"人对 Agent 的隐性补贴"。人会自动去问，Agent 会自动去猜。**

**第二步：写成契约**

```yaml
rule_id: PROC-TENDER-001
scope: 采购申请提交时
condition:
  metric: 申请金额（不含税，人民币，两位小数）
  aggregation: 单笔
  operator: ">"
  threshold: 800000
action:
  require: [招标流程, 采购办复核]
  block: true
on_condition_unmet:
  action: 走普通询价流程
on_data_missing:
  action: 阻断并提示补充（禁止默认放行）
boundary_policy:
  exactly_equal: 不触发（需评审确认）
  split_detection: 同供应商 90 日内累计超 80 万，提示人工复核
```

**第三步：对比一下差别在哪**

| | 人话需求 | 能力契约 |
|---|---|---|
| 边界 | 靠问 | 穷举（等于 80 万怎么办） |
| 口径 | 靠猜 | 写在字段里（不含税、单笔） |
| 缺失数据 | 靠默认 | **显式规定"必须阻断"** |
| 可测试 | 难 | 直接可生成用例 |
| 变更 | 改一句话 | 改配置 + 跑回归 |

**最值得学的是 `on_data_missing` 那一条**。人类系统里，"数据缺失"通常走默认值放行——因为报错会被人投诉。**但默认放行在 Agent 场景是危险的**：Agent 会不断触发这个分支，每次都静默放行，最后没人知道有多少单是"因为查不到税而按不含税处理的"。

> **一条硬规则：给 Agent 的系统，缺数据时默认"阻断"，不默认"放行"。** 因为人会被阻断逼着去补数据，Agent 不会。

## 3.4 需求环节的一个结构性变化：验收标准前置

传统流程里，验收标准常在开发完成后由测试同学补。**在 Agent 参与的流程里，这必须反过来。**

原因很直接：如果验收标准后置，你就无法判断"Agent 交付的是不是你要的东西"，只能靠读代码。而读 Agent 写的代码，**成本可能高于自己写**——这是 AIDev 那份数据里"接受率低"的另一面：不是不信任，是**审查成本太高**。

$$
\text{净收益} \;=\; \underbrace{C_{\text{自己写}}}_{\text{构造}} \;-\; \underbrace{\big(C_{\text{委派}} + C_{\text{审查}} + C_{\text{返工}}\big)}_{\text{委派 + 验证 + 修正}}
$$

**这个式子说的是**：用 Agent 是不是划算，不取决于它写得多快，取决于"审查 + 返工"能不能压到比自己写还低。**而压低审查成本最有效的办法，就是让验收标准变成可自动执行的检查。**

所以需求阶段的产出物，从"一份文档"变成"**一份文档 + 一套验收检查**"。这套检查可以是测试用例、可以是 schema 校验、可以是一组断言——但必须**机器可判**。

# 四、设计：从"界面设计"到"上下文设计"

## 4.1 一个新问题：Agent 在做决定时，看到的是什么

人类用软件时，看到的是**界面**。Agent 用软件时，看到的是**上下文**——工具列表、参数说明、错误信息、以及前面几轮的对话历史。

这带来一个全新的设计对象：**上下文预算内的信息组织**。

| 传统设计关注 | Agent 时代新增关注 |
|---|---|
| 界面布局、交互流程 | 工具列表的组织与命名（Agent 靠名字选工具） |
| 错误提示文案 | 错误的**可操作性**（能不能重试、要不要改参数） |
| 权限的角色划分 | **Agent 的身份与权限边界**（它能代表谁做事） |
| 数据的展示形式 | 数据的**可引用性**（能不能带出处） |

## 4.2 四条设计原则

**① 工具的"命名即路由"**

Agent 选工具，主要靠**名字和描述**。所以：

| 差 | 好 | 为什么 |
|---|---|---|
| `process()` | `create_purchase_request()` | 名字本身说明动作与对象 |
| `query(sql)` | `search_orders(status, date_range, limit)` | 别让 Agent 写 SQL，它会写出危险的 SQL |
| `do_stuff()` | `submit_approval(approval_id)` | 一个工具只做一件事 |

**第二行值得展开**：给 Agent 一个裸的 SQL 执行接口，等于给它 `DROP TABLE` 的权限。**能力边界要在工具设计时就切好，不能指望 Agent 自律。**

**② 错误信息要"可编程"**

```json
{
  "ok": false,
  "code": "BUDGET_EXCEEDED",
  "message": "预算余额不足",
  "retryable": false,
  "details": {"required": 900000, "available": 600000},
  "suggested_action": "REDUCE_AMOUNT_OR_SPLIT"
}
```

**为什么这几行比"友好提示"有价值**：Agent 能据此判断"不该重试、应该拆单"。而如果只返回"操作失败，请稍后重试"，Agent 会重试——重试十次，每次都失败。

**③ 幂等键必须暴露给调用方**

$$
\text{结果}(k) \;=\; \text{第一次调用}(k), \qquad \forall\, \text{后续同 } k \text{ 的调用}
$$

**这个式子说的是**：客户端生成一个幂等键 $k$，服务端保证同一个 $k$ 只有第一次生效，后续调用都返回第一次的结果。这样 Agent 可以放心重试。

**④ 权限设计要从"人"扩展成"人 + Agent + 委托关系"**

传统权限是企业组织架构的映射。Agent 加入后，出现三种新关系：

| 关系 | 问题 | 处理 |
|---|---|---|
| **代行** | Agent 代表某个用户操作，权限等于该用户吗？ | 通常应**等于或小于**用户权限，不能超集 |
| **多跳** | Agent A 调用 Agent B，B 的权限怎么算？ | 需要**委托链**，每一跳都要可审计 |
| **聚合** | Agent 汇总多个用户的数据做分析，算越权吗？ | 需要"聚合视图"这一权限类型 |

**第二条是最容易被忽略的**。多 Agent 协作里，权限会在调用链上"衰减"或"放大"，而传统 RBAC 模型没有表达"委托链"的能力。

## 4.3 设计产出物多了一样东西：Agent 的"使用说明"

以前的设计文档写给人看，现在还要写一份给 Agent 看：

| 内容 | 作用 |
|---|---|
| 这个系统能做什么（能力清单） | 让 Agent 自己发现 |
| 每个能力的适用与不适用场景 | 减少误用 |
| 典型调用序列 | 教 Agent 正确的用法顺序 |
| 已知限制与失败模式 | 让 Agent 知道"什么时候该停下来问人" |

**最后一条是新增且关键的**：把"我不知道该怎么办"变成 Agent 的一个合法输出。否则它会在信息不足时硬猜。

# 五、开发：从"写实现"到"写约束"

## 5.1 三种工作形态并存，而不是替代

现实中不是"Agent 全写"，而是三种形态按场景分布：

| 形态 | 适合什么 | 人的角色 |
|---|---|---|
| **人写** | 核心算法、安全边界、性能关键路径 | 全责 |
| **Agent 写 + 人审** | 业务逻辑、CRUD、胶水代码、测试 | 审查者 |
| **Agent 写 + Agent 审** | 重复性高、有强验证手段（单测、类型、lint） | 抽检者 |

**判断标准很简单**：**这个产出的对错，能不能被自动判定？**
- 能（有单测、有类型、有 schema）→ 可以交给 Agent 自循环；
- 不能（涉及业务判断、性能权衡、安全边界）→ 必须有人。

## 5.2 工程师的主要工作变成了"写约束"

在 Agent 参与的开发里，工程师花时间最多的地方，从"敲代码"变成"写让 Agent 不跑偏的东西"：

| 约束形式 | 例子 | 作用 |
|---|---|---|
| **仓库约定文件** | `CLAUDE.md` / `AGENTS.md`：构建命令、目录约定、禁忌 | 减少重复交代 |
| **类型与 schema** | 强类型接口、JSON Schema | 编译期拦截大部分错误 |
| **测试与断言** | 单测、快照测试、不变式 | 运行期判定对错 |
| **架构约束** | 分层规则、依赖方向（可用 lint 强制） | 防止结构腐化 |
| **禁止清单** | 不许引入新依赖、不许改某目录 | 防止"顺手优化" |

**这里有一个反直觉的结论**：

> **约束写得越具体，Agent 越好用；而这要求你对代码库的理解比"自己写"时更深。**

因为自己写的时候，你不需要说清"为什么不能用某个方案"——你知道。而要让 Agent 不犯这个错，你必须把它写下来。

**所以"不学底层"这个推论在这里第一次失效**：要给 Agent 写有效约束，你必须比它更懂底层。**抽象层越高，对底层的理解要求不是降低，而是变成了"用于判断"而不是"用于实现"。**

## 5.3 代码审查的性质变了

| | 传统审查 | Agent 代码的审查 |
|---|---|---|
| 关注 | 逻辑正确、风格一致 | **逻辑正确 + 意图一致**（它做的是我要的吗） |
| 规模 | 几十到几百行 | 可能几千行（因为产出便宜） |
| 技巧 | 逐行读 | **抽样式验证 + 依赖自动化检查** |
| 最大风险 | 漏掉边界 | **看起来对但整体方向错** |

**第二行是新的矛盾**：Agent 让产出变便宜，于是 PR 变大、变多——**但人的审查能力没有变强**。AIDev 的数据已经显示了这个后果：提交量上去了，接受率下来了。

这直接催生了新的工程需求：**降低审查成本的技术**（更小的变更单元、更强的自动化验证、变更影响分析），会成为未来几年的重点。

## 5.4 七个常见问题

| # | 症状 | 根本原因 | 对策 |
|---|---|---|---|
| 1 | Agent 反复传错参数、编出不存在的字段 | 工具只有自然语言描述，没有参数 schema | 参数必须 JSON Schema，枚举要穷举 |
| 2 | 报错后无限重试，成本爆炸 | 错误信息只有一句"操作失败" | 返回 `code` + `retryable` + `suggested_action` |
| 3 | 重复下单、重复扣款、重复发通知 | 接口不幂等，而 Agent 重试是常态 | 暴露幂等键，服务端去重 |
| 4 | Agent 明明有正确的工具却选了错的那个 | 工具太多、名字太像、描述重叠 | 按场景分组下发，工具名带动作和对象 |
| 5 | Agent 在信息不足时硬编一个答案 | 没有"停下来问人"的合法出口 | 提供 `ask_user` 类工具并写进提示 |
| 6 | 改了提示词，效果突然崩了，回滚发现"代码没变" | 提示词/模型版本不在发布单元里 | 提示词进版本库，与模型版本一起发布 |
| 7 | 上线后偶发错误答案，日志全绿查不出来 | 错误是"语法对、语义错" | 抽样在线评测 + 结果断言 |

**第 4 条最反直觉**：直觉上"工具越多 Agent 越强"，实际上**工具越多，路由越容易错**。这是典型的"选择过载"——一个能访问 50 个工具的 Agent，在简单任务上的正确率往往低于只有 5 个工具的 Agent。所以**上下文预算内的工具编排，本身就是设计的一部分**。

**第 7 条最难修**：因为它不触发任何传统告警。这类问题的唯一解是**按语义评测**，而不是按错误率监控。

# 六、测试：从"最后一道关"到"主要质量来源"

## 6.1 测试的地位发生了反转

传统流程里，测试是"开发完之后检查一下"。在 Agent 参与的流程里，**测试是质量的主要来源**，因为：

- 构造变便宜 → 缺陷密度不会降低，但缺陷总量上升；
- 人的审查能力有限 → 靠人眼看不住；
- **测试是唯一能自动化、可重复、能进入 Agent 自循环的验证手段**。

**换句话说：测试从"成本项"变成了"生产能力"。**

## 6.2 三层测试，各有分工

| 层 | 检查什么 | 谁来写 | 能不能全自动 |
|---|---|---|---|
| **单元/类型/schema** | 局部正确性 | Agent 写，人抽检 | 能 |
| **集成/契约** | 组件之间是否对得上 | 人定契约，Agent 写用例 | 半自动 |
| **端到端/场景** | 业务意图是否实现 | **人写**（这是核心资产） | 不能 |

**第三层是关键**：端到端用例是"意图的编码"，它定义了"什么叫对"。这部分**不能交给 Agent 写**——否则等于让被考的人出考卷。

## 6.3 一个新的测试对象：Agent 本身的行为

如果你的系统里**有 Agent 在跑**（不只是用 Agent 写代码），测试对象就多了一层：

| 测什么 | 怎么测 | 难点 |
|---|---|---|
| **单步准确性** | 给定输入，输出是否符合预期 | 输出是自然语言，判定难 |
| **多步收敛性** | 给定任务，能否在有限步内完成 | 路径不唯一，难以断言 |
| **越界行为** | 会不会调用不该调的工具 | 需要"能力沙箱" |
| **失败恢复** | 工具报错后能否正确降级 | 需要构造故障 |
| **成本与延迟** | 完成一个任务花多少 token、多少秒 | 波动大，要统计 |

**第二行是新的**。传统软件测试断言"输出等于某值"；Agent 的测试要断言"**在预算内达成目标**"——允许多条路径，但要求收敛。

**第四行也值得强调**：Agent 的失败恢复能力，比它的成功率更重要。一个成功率 95% 但失败后会乱来的 Agent，比一个成功率 85% 但失败后会停下来的 Agent 危险得多。

## 6.4 评价指标也要换

$$
\text{有效吞吐} \;=\; \frac{\text{被接受并合入的变更数}}{\text{人 · 天}}
$$

**这个式子的意义**：不要考核"生成了多少代码"或"提交了多少 PR"——那些指标会鼓励刷量。要考核**被人接受并合入的变更**，因为它同时包含了"产出"和"验证通过"两层含义。

这也正好对上 AIDev 的发现：**提交量不是能力，接受率才是。**

# 七、运维：从"监控指标"到"可观测 + 可归因"

## 7.1 Agent 系统运维的两个新问题

传统运维监控的是"系统状态"：CPU、QPS、错误率、延迟。

Agent 系统还要监控"**行为**"：

| 新问题 | 例子 | 需要的观测 |
|---|---|---|
| **它做了什么** | Agent 调了哪些工具、按什么顺序 | 完整的执行轨迹（trace） |
| **它为什么这么做** | 为什么选了 A 工具而不是 B | 决策依据（检索到什么、提示是什么） |
| **它花了多少** | 一个任务烧了多少 token | 成本归因到任务/用户 |

**第二行是最难的**：传统系统里"为什么"由代码决定，可以读代码；Agent 的"为什么"是一个概率决策，**只能靠记录当时的输入**。

## 7.2 可观测性的三根支柱要加一根

| 支柱 | 传统 | Agent 时代 |
|---|---|---|
| **日志** | 事件记录 | 事件 + **决策记录**（选了什么、为什么） |
| **指标** | 数值时间序列 | 加上**语义指标**（任务成功率、平均步数、人工介入率） |
| **追踪** | 请求链路 | 加上**Agent 的执行树**（含子 Agent 分叉） |
| **（新增）评测** | —— | **在线评测**：抽样打分，发现"看起来正常但结果错" |

**第四根是最容易被忽略、但最关键的**。因为 Agent 的错误往往是"语法正确、语义错误"——日志没报错、指标都正常、链路完整，但结果就是错的。**只有按语义评分才能发现。**

## 7.3 变更管理的新麻烦

Agent 系统的"变更"不只包括代码，还包括：

| 变更类型 | 影响 | 传统方法够不够 |
|---|---|---|
| 提示词修改 | 行为大幅变化 | ❌ 提示词不在版本库里 |
| 模型升级 | 行为漂移（同提示不同结果） | ❌ 模型不是"你的代码" |
| 工具增删 | 可选空间变化，路由改变 | ⚠️ 部分 |
| 检索库更新 | 决策依据变化 | ⚠️ 部分 |

**核心矛盾**：传统 CI/CD 假设"同一份代码 + 同一份配置 = 同样的行为"。Agent 系统里，**这个假设不成立**——模型版本一变，行为和结果都可能变，而代码一行没改。

**对策**：把"提示词、模型版本、工具集、检索库版本"一起纳入**可回滚的发布单元**，每次发布都跑固定的评测集。这不是"新方法"，是把传统发布流程的假设**修正成"行为等价"而不是"代码等价"**。

# 八、协作与组织：瓶颈从"生产"移到"验收"

## 8.1 一条价值链的判断

软件交付的五个环节，抽象成本的变化并不均匀：

| 环节 | 抽象化程度 | 瓶颈是否转移 |
|---|---|---|
| 需求 | 低（意图难以形式化） | **成为瓶颈** |
| 设计 | 中 | 部分转移 |
| 编码 | **高（已被大幅抽象）** | 已不是瓶颈 |
| 测试 | 中（部分可自动） | 部分转移 |
| 运维 | 中 | 部分转移 |

**读法**：编码是唯一被彻底抽象的环节。所以"提速"最明显，但**提升的是最不瓶颈的那一段**——这就是为什么很多团队感觉"AI 写代码快了很多，但交付没快多少"。

这正是 **阿姆达尔定律**在软件交付上的投影：

$$
S \;=\; \frac{1}{(1-p) + \dfrac{p}{s}}
$$

**这个式子说的是**：如果只有比例 $p$ 的工作被加速 $s$ 倍，整体加速比 $S$ 的上限是 $1/(1-p)$。编码若占交付周期的 30%，即使编码快到无穷，整体最多快 1.4 倍。

**所以真正的收益不来自"编码更快"，而来自"把瓶颈环节也抽象掉"**——也就是需求标准化、验证自动化。

## 8.2 岗位与技能的重心

| 角色 | 重心变化 |
|---|---|
| 开发 | 从"实现"到"约束 + 审查" |
| 测试 | 从"执行用例"到"**设计可自动判定的验收标准**" |
| 产品 | 从"写故事"到"**写可判定的契约**" |
| 运维 | 从"保稳定"到"**行为可观测 + 可归因**" |
| 架构 | 新增"Agent 可用性"这一设计目标 |

**最值得注意的一行是"产品"**。因为需求是新的瓶颈，而需求的形态正在从"文档"变成"契约"——这要求产品经理具备**把模糊需求变成可判定条件**的能力。这是一个真实存在、但还没被普遍重视的技能缺口。

# 九、技术与研究前瞻：五个值得关注的方向

只说"会发展"，没有信息量。下面五个方向，各有明确的待解问题。

## 9.1 接口层：从"能调"到"可协商"

现状：MCP 这类协议解决了"工具怎么描述"。
待解：**工具之间怎么协商**——A 工具的输出格式不匹配 B 工具的输入，现在靠人写适配层。未来的方向是让工具自己声明"我需要什么、我产出什么"，由编排层自动匹配。

## 9.2 验证层：从"单测"到"意图验证"

现状：验证依赖人写测试。
待解：**如何验证"实现的是意图"**，而不只是"通过了测试"。这是"看起来对但整体错"这类缺陷的唯一解。相关方向包括形式化规约、基于属性的测试（property-based testing）、以及用另一个模型做交叉验证。

## 9.3 治理层：Agent 的身份与责任

现状：Agent 用人的身份操作，权限边界模糊。
待解：**Agent 的独立身份、委托链、操作审计、责任归属**。这不是技术问题，是技术与合规交叉的问题——尤其在金融、医疗、政务场景，**"谁为 Agent 的操作负责"必须能回答**。

## 9.4 评测层：从静态基准到在线评测

现状：用固定数据集（如 SWE-bench）评测，容易被污染、被过拟合。
待解：**持续演进的、与业务目标对齐的在线评测**。AIDev 这类"从真实生产数据中观察行为"的方法，会比静态基准更有生命力。

## 9.5 经济学层：成本归因与定价

现状：按 token 计费，但一个任务的成本取决于步数、重试、上下文长度，波动巨大。
待解：**把成本归因到"任务"而不是"调用"**，才能做出有意义的 ROI 判断。这也决定了 Agent 类产品怎么定价（这是另一个专门的话题）。

# 十、这个类比在哪里会失效

前面所有论证都建立在"抽象层像编译器一样可靠"这个前提的**否定**上。这一节把反面说透——因为如果只讲"倒转"，文章会变成另一种口号。

## 10.1 失效一：汇编有确定语义，Agent 没有

汇编的行为由 CPU 定义，**是确定性的**。同一段汇编，跑一万次结果一样。
Agent 的行为由概率分布定义，**同输入不同输出是常态**。

**这个差别导致一个直接后果**：汇编可以"验证一次，永久相信"；Agent 必须"**持续验证**"。评测集不是上线前跑一次，而是每次变更都要跑。

## 10.2 失效二：没有"编译器保证"，就没有"不用懂底层"的资格

这是最重要的一条。

编译器让你可以不懂汇编，因为**它替你保证了等价性**。Agent 没有这个保证，所以：

> **你不懂底层，就无法判断 Agent 做得对不对。而判断不了，就等于没有交付。**

所以正确的表述不是"以后不用学底层"，而是：

> **以后学底层的目的，从"用它实现"变成"用它判断"。**

类比一下：一个从没读过汇编的程序员，遇到"性能瓶颈在 cache miss"时，仍需要能看懂反汇编来定位。**Agent 时代不是消灭了这个需求，而是把它从"日常必备"变成"关键时刻必备"——但"关键时刻"一点没减少。**

## 10.3 失效三：抽象泄漏的地方，恰恰是最贵的地方

软件工程有个老规律：**抽象都会泄漏**，而泄漏的地方往往是成本最高的地方（性能、并发、分布式、安全）。

Agent 的抽象层不但会泄漏，而且**泄漏时不会报警**——它给你一个跑得通但错的实现。

**这意味着**：越靠近这些"高成本区域"（核心算法、并发控制、安全边界、性能关键路径），越不能依赖高层抽象。**"跟 Agent 打交道"这个技能，在这些区域是无效的。**

## 10.4 失效四：责任不能委托

法律和合规上，**Agent 不能承担责任**。出了事故，"是 Agent 决定的"不是免责理由。

**所以有一条硬边界**：**凡是需要有人签字的决策，就不能完全交给 Agent。** 这不是技术限制，是制度设计。它意味着：

- Agent 可以做"建议者"，不能做"决策者"（在高风险场景）；
- 人必须保留"看懂并能否决"的能力；
- 而"看懂"，又回到了 10.2——**你得懂底层**。

## 10.5 失效五：这个转变是渐进的，不是断代的

最后一盆冷水：**"上一个时代面向人，下一个时代面向 Agent"这个二分法，本身是简化的。**

真实情况是：**两套消费者长期并存**。财务报表还要人看，监管报表还要人签，客户还要能打电话找人。所以基础设施的形态会是"**双形态**"——同一份数据，既有给人看的视图，也有给 Agent 用的接口。

**这带来一个实际的设计约束**：**两套形态必须同源**。如果"给人看的报表"和"给 Agent 用的接口"是两套独立实现，它们**迟早会对不上**——而对不上的时候，没人知道该信哪个。

$$
\text{一致性要求}:\quad \text{视图}_{\text{人}} \dashv \text{模型}_{\text{唯一}} \dashv \text{接口}_{\text{Agent}}
$$

**这个式子说的是**：人和 Agent 的两种视图，都必须从同一个底层模型派生（$\dashv$ 表示"从……派生"）。**不能各建一套。**

# 十一、给工程师的六条建议

**① 首先明确"验收标准"**

每接一个任务，先写"怎么算完成"，再动手。这件事的价值在这个时代被放大了十倍——因为它同时服务于**你自己**（想清楚）和**Agent**（判定标准）。

**② 学会写约束，而不只是写代码**

仓库约定文件、类型、lint 规则、禁止清单——这些"元工作"的 ROI 远高于多写几个函数。判断标准：**你写下的约束，能不能阻止一类错误？**

**③ 保留"读懂底层"的能力，但换用途**

不用再背汇编、手写 SQL 优化，但要能**看懂**：这段代码为什么慢、这个并发有没有竞态、这个权限设计有没有越权。**用途从"实现"变成"审查"。**

**④ 优先投资"可自动判定的检查"**

测试、schema、类型、断言、不变式——任何能自动判对错的东西，都在放大你的产能。反之，任何"只能靠人看"的环节，都会成为新瓶颈。

**⑤ 关注"接受率"而不是"产出量"**

对个人和对团队都一样。产出多但被退回多，等于零。**有效吞吐 = 被接受的变更 / 人天**。

**⑥ 在高风险区域保持"手写"的自觉**

核心算法、安全边界、资金相关逻辑——这些地方不要图快。不是因为 Agent 不行，是因为**这些地方的错误代价，远高于省下来的时间**。
