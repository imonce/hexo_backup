Claude Code、Codex、Hermes、OpenClaw、Manus 横向拆解

Posted on 2026-07-04 Edited on 2026-11-11 Views: Valine:

导语

2026 年的编码 Agent 市场已经过了”能不能写代码”的阶段，进入”能不能嵌进工程系统“的阶段。但市面上的对比文章普遍存在一个方法论错误：把厂商封闭的编码产品、可自托管的 Agent 运行时、通用任务 Agent 放在同一维度上打分。

结果是：Claude Code 在”本地部署友好度”上输给 OpenClaw，OpenClaw 在”开箱代码质量”上输给 Claude Code，两边都不服。这不是产品差距，是比较维度错配。

本文做三件事：

  1. 先建立分类坐标系，把五者按”控制权归属”和”抽象层级”放回各自位置；
  2. 在六个真实影响工程决策的维度上做对比（本地部署、长代码库理解、工具调用、调试闭环、上下文、开源协议）；
  3. 拆开 Vibe Coding 这个概念——它被严重误读，大多数人争论的是它的输入形式，而它的判别标准其实在验收环节。

时效性声明：本文数据核对时间为 2026-11-11。编码 Agent 是月度迭代的品类，模型名、版本号、价格在一个季度内都可能变化。凡涉及具体版本与数字，均标注来源；属于工程判断的评分，明确标注为主观评估。

1. 坐标系：先分清”产品””运行时””通用 Agent”

1.1 一张定位表

本质是什么 谁控制执行环境 模型绑定 编码是
Claude Code 厂商自研的终端编码 Agent（闭源产品） 你的机器，但 harness 由 Anthropic 控制 强绑定 Claude 系列 唯一主业
Codex 厂商编码 Agent 产品线（CLI/App/Cloud/IDE 四形态） 本地或 OpenAI 云沙箱 强绑定 GPT 系列 唯一主业
Hermes 开源自进化 Agent 框架（Nous Research） 你的服务器 无绑定，可接本地模型 能力之一
OpenClaw 开源自托管 Agent 运行时 + 网关 你的设备 无绑定，模型/harness 皆插件 能力之一
Manus 云端通用任务 Agent（SaaS） Manus 云虚拟机 不透明（自研调度） 子能力之一

1.2 分类带来的三个直接结论

结论一：只有两个是”编码专用产品”。
Claude Code 和 Codex 的全部设计取舍都围绕”让代码变更落地”：读仓库、改文件、跑测试、提 PR。它们的 harness 是垂直优化的，所以在单点编码任务上的效率上限最高，代价是你无法改它的行为逻辑。

结论二：OpenClaw 和 Hermes 卖的不是”编码能力”，是”控制权”。
它们提供 Gateway、会话、记忆、技能、通道接入这套运行时，模型是可替换件。编码能力来自你接的模型和装的 skill/plugin。所以拿它们和 Claude Code 比”代码写得好不好”，本质上是在比你配的那个模型，而不是比产品。

结论三：Manus 的对手不是编码工具，是”交付物”。
Manus 的核心抽象是”给一个任务，产出可用的东西”——网站、报告、PPT、数据分析。写代码只是达成交付物的手段之一。用 Manus 做 20 万行 Java 单体仓库的重构，是选错了工具；用它两小时搭一个带后端和登录的 MVP，才是它的甜点区。

1.3 一个容易忽略的事实：harness 比模型更决定体验

同一个模型，套不同 harness，在长任务上的成功率差异可以达到数十个百分点。原因在于 harness 决定了：

  • 上下文怎么组织（全量塞 / 检索 / 子 Agent 隔离 / 压缩时机）
  • 工具怎么暴露（工具数量、描述质量、是否按需加载）
  • 失败怎么恢复（重试策略、检查点、回滚）
  • 验证怎么做（能否跑测试、能否读 CI、能否自测）

所以”某模型在 Terminal-Bench 上 91.9%”这类数字，衡量的是模型 + 官方 harness 的组合，不是你把它接进自己框架后的表现。这一点在做技术选型时经常被忽略。

2. 逐个拆解

2.1 Claude Code：把”工程闭环”做到极致的闭源终端

定位：终端优先的编码 Agent，故意不做 GUI。设计哲学是”嵌入已有工作流”，而不是”再造一个 IDE”。

底层模型：Claude 系列，无法切换。2026 年的旗舰线包括 Claude Fable 5、Sonnet 5、Opus 4.8 等（具体档位随订阅变化）。强绑定是产品决策而非技术限制——它换来了对执行边界和工具行为的完全掌控。

核心能力（2026 年形态）：

能力 机制 工程价值
CLAUDE.md 项目级常驻约定文件 把团队规范从”每次口述”变成”仓库资产”
Subagents 独立上下文的子 Agent 探索过程不污染主上下文，天然隔离噪声
Skills SKILL.md + 资源，渐进式加载 把流程知识变成可版本管理的文件，token 与技能数解耦
Hooks 生命周期钩子（工具调用前后） 确定性管控：格式化、拦截危险命令、审计
MCP 标准工具协议 接外部系统，不用自己写适配
Plugins Skills + Commands + Agents + Hooks 的打包 团队级分发
Checkpoint / 回滚 会话级快照 长任务失败可回到已知好状态

这套东西的本质是：把”Agent 的行为”从 prompt 里的软约束，变成仓库里的硬资产。Hooks 尤其关键——它是唯一能在模型之外强制执行规则的地方（模型可以忽略 prompt，但不能忽略 hook）。

部署形态：本地 CLI（Node.js 运行时），也可通过 /teleport 把会话迁移到云端继续。没有自托管版本，执行在你的机器上，但 harness 与遥测受厂商控制。

关键取舍：只服务会用终端的人。产品经理、运营、非技术创始人一律用不了。这是它的天花板，也是它在专业开发者中渗透率高的原因——窄产品赚时间，宽产品赚流量。

参考：Claude Code 2.1.x 系列在 2026 年初密集更新 Agent 能力、开发者体验与安全性（腾讯新闻，2026-01-09）；年化收入据路透社 2026 年 2 月披露突破 25 亿美元、企业订阅占比过半（二手报道，人人都是产品经理，2026-05-08）。

2.2 Codex：从 CLI 长成”四形态 + 云环境”

定位：OpenAI 的编码 Agent 产品线。和 Claude Code 最大的结构性差异是：它不把”本地终端”当唯一入口，而是把同一个 Agent 铺到四种执行环境上。

四种形态（截至 2026 年中）：

形态 执行位置 适合
CLI 本地终端（Rust 实现，Apache-2.0 开源） 终端党、脚本化、CI 内嵌
App（桌面） 本地 不想开终端但要素材本地权限
Cloud（Web） OpenAI 云沙箱，接 GitHub 并行派发多个任务、离线跑
IDE 插件 编辑器侧边栏 需要看 diff 逐行确认

2026 年 9 月 DevDay 进一步引入可复用云端开发环境——同一环境可从任意设备接入，把”我的开发机”变成云上持久对象（品玩/TechCrunch，2026-09-30）。这是和 Claude Code”本地优先”路线的根本分歧：**Codex 赌的是”开发环境应该像容器一样可编排”，Claude Code 赌的是”开发者的机器就是最好的沙箱”**。

底层模型：GPT-5.x-Codex / GPT-5.6 系列。2026 年 8 月的公开数据中，GPT-5.6 Sol 在 Terminal-Bench 2.1 上为 88.8%，Sol Ultra 为 91.9%；Claude Fable 5 为 83.1%，Opus 4.8 为 78.9%（引自二手汇总，人人都是产品经理，2026-08-12；benchmark 存在污染与 harness 依赖问题，不建议作为唯一选型依据）。

核心能力：任务并行、PR 自动生成与自审、AGENTS.md 作为仓库级约定、云端环境快照、Codex Security CLI（Apache-2.0，做仓库级安全扫描）。

部署形态：CLI 可自托管执行；Cloud 为托管服务；整体是”开源客户端 + 闭源服务”的混合模式。

关键取舍：云端并行是它最强的差异化，但也是最大的约束——你的代码要出网。金融、军工、部分医疗场景直接出局。

2.3 Hermes：把”自我进化”当第一性原理的框架

定位：Nous Research 于 2026 年 2 月发布的开源自改进 Agent 框架，slogan 是 “The agent that grows with you”。它不是编码工具，是一个带学习闭环的通用 Agent 运行时。

底层模型：不绑定。支持 Ollama 本地模型、OpenAI/Claude 系列、以及任意 OpenAI 兼容接口。这既是优点（隐私与成本可控），也是缺点（效果强依赖你接的模型，弱模型 + 自进化会放大错误）。

核心机制：学习闭环

它的差异点不在工具数量，而在”经验怎么沉淀”：

  1. 执行 → 记录工具调用链与结果；
  2. 评估 → 用反馈/结果判定这次任务的好坏；
  3. 抽象 → 把成功的流程抽成可复用技能，写入技能库；
  4. 复用 → 后续任务检索技能并加载。

有公开分析指出其自进化环节结合了 GEPA 类的提示进化（生成变体 → 追踪表现 → 按适应度更新策略库），并配合复杂度筛选与反思抽象（php.cn，2026-05-19，属技术解读，非官方论文）。

核心能力：跨会话持久记忆、技能自动生成与复用、全平台消息网关（Telegram / 飞书 / 企业微信 / Slack / Discord）、工具调用、定时任务。

部署形态：自托管（你自己的服务器），数据不出内网。MIT 协议，可商用、可修改。

生态数据：2026 年 4 月公开报道为 17K Stars、207 位贡献者、上线两个月（人人都是产品经理，2026-04-04）；技能市场 agentskills.io 收录 131 个技能（72 内置 + 59 可选），覆盖 26+ 类别（人人都是产品经理，2026-05-08）。

关键取舍：MIT + 自托管 + 自进化，是研究和私有化场景的最优解；但**”自动生成的技能”没有强制验证器**，这是它最大的工程风险——错误流程会被固化进技能库，然后被反复调用。

2.4 OpenClaw：把 Agent 做成”个人基础设施”

定位：开源自托管 AI 助手/Agent 运行时，2025 年底由 Peter Steinberger 起手，2026 年 1 月下旬爆红（曾用名 ClawdBot、Moltbot）。现在的官方叙事是”你的助手，跑在你的设备上，出现在你的聊天软件里”。

底层模型：完全解耦。官方明确”Models and agent harnesses (Claude, Codex, local models) are plugins you can swap”——它甚至可以把 Claude Code、Codex 当成自己的 harness 插件。这是理解 OpenClaw 的关键：它卖的是编排层，不是模型能力。

架构：

组件 作用
Gateway 本地控制平面：会话、工具、事件、通道路由
Channels Discord / iMessage / Slack / Teams / Telegram / WhatsApp 等 20+ 入口
Companion apps & nodes 语音、Canvas、摄像头、屏幕、设备本地动作
Tools / Skills / Plugins 能力扩展，Plugin SDK + ClawHub 分发
Sandboxing 可选；默认主会话工具直接跑在宿主机

核心能力：多通道接入、持久化记忆与凭据本地存储、Skills（SKILL.md）、MCP、Code Mode、Workboard 会话管理、定时自动化、异地完整备份（可到 Cloudflare R2）。

2026 年 10 月的 v2026.10.1（402 位贡献者、2425 PR、3055 commits）做了两个方向性更新（36氪/机器之心，2026-10-12）：

  • skills_search + skills_read**：不再把所有技能目录塞进 prompt，改为先检索、再按需读全文**。这是解决”技能数量 vs 上下文预算”矛盾的正确做法，值得所有做 skill 系统的团队抄。
  • MCP Apps：把 MCP 工具的交互界面直接开在聊天区旁边，人可以在表单里填参数、确认授权。

部署形态：纯本地自托管（macOS / Linux / Windows / Docker / Nix），MIT 协议，无付费层、无托管服务，由独立 501(c)(3) 基金会治理。企业侧有 OCE（OpenClaw Enterprise）控制平面，定位是”Agent 版的 Kubernetes”，目前未发 1.0，仅适合内部试点（腾讯新闻/至顶科技，2026-10-14）。

关键取舍：能力上限极高（能读你的文件、跑你的命令、发你的消息），但权限也是真的高。官方 README 直接写了 “Tools run on the host for the main session unless you configure sandboxing”——这意味着默认配置下，一个提示注入就可能变成宿主机命令执行。NVIDIA 的 NemoClaw 用 OpenShell 做内核级沙箱、网络策略和审计日志，本质是在补这块（w3cschool/Ollama 文档）。

2.5 Manus：云端通用 Agent，编码只是手段

定位：通用任务 Agent，产物导向。2025 年 3 月由中国团队 Monica.im（蝴蝶效应）发布，2025 年 10 月推出 Manus 1.5。

底层模型：不公开具体模型与调度策略。对外呈现的是”多智能体协作 + 云端虚拟机”的黑箱。

核心能力（Manus 1.5）：

  • 全栈 Web 应用开发：对话式产出带持久化后端、数据库、用户认证、嵌入式 AI 的应用，不用离开平台处理托管与部署；
  • 集成浏览器自测：启动应用、像真实用户一样交互、发现问题并自主修复——这是它最有价值的一环，因为它闭合了 verify loop；
  • 研究 + 内容 + 图像 + 幻灯片的单上下文串联：一个任务里完成”调研 → 建站 → 分析数据 → 出 PPT”；
  • 协作与资料库：多人共享会话，产物集中管理。

官方称 1.5 架构使平均任务时长从 4 月的 15 分钟降到不足 4 分钟，内部基准任务质量 +15%、满意度 +6%；分 Manus-1.5 与 1.5-lite 两档，lite 全量开放、订阅用户有积分折扣（观猹产品页）。

部署形态：纯 SaaS，云端虚拟机执行，不可本地部署。计费为订阅 + 积分/credits。

关键取舍：它优化的是”从想法到可交付物”的端到端时长，不是”在既有代码库里的精确变更”。所以它对绿地项目（从零开始）极强，对棕地项目（几十万行遗留系统）帮助有限——因为它没有你内网的仓库、CI、私有依赖。

3. 六维横向对比

3.1 总表

下表中”技术事实”列来自公开资料（截至 2026-11-11）；”评估”列为主观工程判断，5 分制，仅供方向参考。

维度 Claude Code Codex Hermes OpenClaw Manus
本地部署友好度 3（本地执行，harness 闭源） 4（CLI 开源 Apache-2.0；云依赖） 5（服务器自托管，MIT） 5（本机自托管，MIT） 1（纯 SaaS）
长代码库理解 5 5 2–3（取决于接入模型） 2–3（取决于 harness/模型） 2（无法访问私有仓库）
工具调用 5（MCP + Hooks + Skills） 5（MCP + 沙箱 + 并行） 4（MCP 生态 + 自生成技能） 5（MCP + Plugins + ClawHub） 3（内置工具为主，扩展性弱）
调试能力 5（跑测试/读 CI/git 操作） 5（云端跑测 + PR 自审） 3（能跑命令，缺专用验证层） 3–4（Code Mode + 沙箱可选） 4（浏览器自测是亮点，但沙箱不可控）
上下文策略 compaction + subagent + skills 渐进加载 云端任务隔离 + 大窗口 持久记忆 + 技能复用 技能检索按需加载 + 会话管理 单任务窗口扩展
开源协议 闭源 CLI/Apache-2.0（服务闭源） MIT MIT 闭源 SaaS

3.2 本地部署友好度：不只是”能不能装”

这个维度要拆成三问，答案经常不一致：

问题 Claude Code Codex CLI Hermes OpenClaw Manus
代码是否出你的机器？ 否（推理走 API） CLI 否；Cloud 是 否（可全本地模型） 否（可全本地模型） 是
能否离线/内网跑？ 否 否 可（配 Ollama） 可（配 Ollama/vLLM） 否
能否改行为逻辑？ 否（只能配 hooks/skills） CLI 可改（开源） 可改（MIT） 可改（MIT） 否

关键判断：真正决定”能不能进内网”的不是客户端是否开源，而是推理是否必须走公网。Codex CLI 开源但依赖 OpenAI API；Hermes/OpenClaw 开源且能接 Ollama，才算完整的内网方案。但要注意——本地模型的能力折损是真实的，用 7B/14B 模型跑 OpenClaw，体验和接 Claude 差一个量级。选”本地”之前先想清楚：你要的是合规，还是省钱？两者结论可能相反。

3.3 长代码库理解：三条技术路线

这是编码 Agent 最核心的能力，业内实际有三条路线，各自代价不同：

路线 代表 机制 优势 短板
Agentic Search（无索引） Claude Code 主流用法 LLM 自己 grep/glob/读文件，多轮收敛 无索引漂移、结果可解释、隐私好、冷启动快 依赖命名规范；仓库越乱越靠模型”猜”；轮次多则慢
语义索引 Cursor 类 IDE 产品 代码切块 + embedding + 向量召回 首轮召回快，跨文件语义匹配强 索引需重建（分支切换、大 monorepo 是痛点）；有隐私顾虑
云端仓库快照 + 并行任务 Codex Cloud 云端完整 clone、装依赖、跑测试 环境一致性最好，可并行 N 个任务 首次环境准备慢；依赖出网

Claude Code 选 1 是刻意的：Anthropic 多次表达过”不做索引”的立场，理由是索引会漂移、会过时，而 grep 的结果永远是真的。工程上的实际差异是：

  • 单文件/邻近文件任务：三者差别不大；
  • 跨 20 个文件追一条调用链：agentic search 的轮次成本显著上升，索引方案更快；
  • 重命名混乱、无类型标注的遗留仓库：agentic search 容易漏，索引的语义召回更有优势。

结论：没有普适最优。代码规范好、类型完整的仓库，agentic search 性价比最高；命名混乱的老仓库，先补类型和命名，比换工具收益大。

3.4 工具调用：MCP 收敛了接口，没收敛”流程”

2025–2026 年最大的变化是工具层协议收敛到 MCP。五个里至少四个支持 MCP（Claude Code、Codex、OpenClaw、Hermes），这意味着”接一个内部系统”这件事的成本从”每家写一个适配器”降到”写一个 MCP server”。

但要分清两个层次：

层 解决什么 代表机制 是否已标准化
工具层 单个原子能力怎么暴露 MCP 事实标准
流程层 一串动作怎么复用 Skills / Commands / Workflow 未标准化，各家方言

这正是 OpenClaw 和 Claude Code 都在做 Skills 的原因：MCP 让你有更多工具，Skills 让你不必每次重新组织工具。而工具越多，选择准确率越低——所以 OpenClaw 在 2026.10 把技能目录改成 skills_search 按需检索，方向是对的。

一个反直觉的工程结论：接 50 个 MCP server 的 Agent 不一定比接 5 个的强。工具描述占上下文、选择空间变大、错误调用率上升。工具集要做”策展”，不是”堆砌”。

3.5 调试能力：能不能闭合 verify loop

“调试能力”不是”能不能改 bug”，而是Agent 能否自己确认改对了。这决定了长任务的收敛性。

验证手段 Claude Code Codex Hermes OpenClaw Manus
跑单测/构建 ✅ ✅ ✅（需配） ✅（需配） ✅
读 CI 日志 ✅ ✅（GitHub 集成） ⚠️ 需自建 ⚠️ 需自建 ❌
浏览器端自测 ⚠️ 需装 Playwright MCP ⚠️ 需配 ⚠️ 需配 ⚠️ 需配 ✅ 内置
提交前人工 diff 确认 ✅ ✅（IDE 形态最佳） ⚠️ ⚠️ ❌（黑箱）
失败回滚 ✅ checkpoint ⚠️ 依赖 git ❌ ❌ ❌

这是我认为Manus 最被低估、也最容易被高估的地方：内置浏览器自测确实闭合了”UI 改完到底对不对”这个环，对绿地 Web 项目价值极高；但它的执行在云端黑箱里，你看不到中间 diff，出问题只能重跑。verifier 强，可观测性弱。

反过来 Claude Code 是verifier 弱一点（要自己配），可观测性强（每一步都能看、能中断、能回滚）。生产环境里，后者通常更重要——因为你需要为结果负责，而不只是拿到结果。

3.6 开源协议：MIT 和 Apache-2.0 的差别比想象中大

项目 协议 商用 修改 专利授权 商标 备注
Claude Code 闭源 按订阅条款 ❌ 无 Anthropic 企业需看 DPA 与数据条款
Codex CLI Apache-2.0 ✅ ✅ ✅ 显式授予 不含商标 含专利 retaliation 条款
Hermes MIT ✅ ✅ ❌ 无明示 不含商标 最宽松，法务最省事
OpenClaw MIT ✅ ✅ ❌ 无明示 不含商标 基金会治理（501(c)(3)）
Manus 闭源 SaaS 按订阅条款 ❌ 无 Manus 数据处理在境外需评估

给企业法务的三条实操建议：

  1. 有专利风险敞口的场景选 Apache-2.0 而非 MIT。MIT 不含专利授权条款，贡献者日后主张专利时你没有明示许可；Apache-2.0 第 3 条明确授予专利许可，并含 retaliation（你起诉别人专利侵权则授权终止）。Codex CLI 在这里更稳。
  2. **MIT 项目要注意”无担保”**。Hermes/OpenClaw 出问题，责任在你自己。
  3. 闭源产品的风险不在协议，在数据条款与可撤销性。订阅制意味着供应商可以改价、改模型、改配额，你的工作流会被动跟着变。

4. Vibe Coding 辨析：被误读的不是输入，是验收

4.1 它到底是什么

2025 年 2 月，Andrej Karpathy 在 X 上发了那句话：

“There’s a new kind of coding I call ‘vibe coding’, where you fully give in to the vibes, embrace exponentials, and forget that the code even exists.”

2025 年底，Collins 词典把 Vibe Coding 选为年度词汇。到 2026 年 8 月，它已经走完了”狂欢 → 反思”的完整周期（人人都是产品经理，2026-08-12）。

定义里其实有两个可分离的成分：

  • (a) 输入侧：用自然语言表达意图，而不是写代码；
  • (b) 验收侧：放弃阅读代码，”forget that the code even exists”，靠运行结果和感觉判断对错。

绝大多数争论混淆了这两者。 用 Claude Code 写代码、但每行 diff 都看过的人，做的是 (a) 而不是完整意义上的 Vibe Coding。判别标准是 (b)：你是否还愿意/能够为这段代码的正确性负责。

4.2 与传统目标驱动式编码 Agent 的思路差异

先明确”目标驱动式”（goal-driven / verifier-driven）是什么：给定目标 + 可执行的验收条件，Agent 迭代直到验收通过。SWE-bench 式的任务、带单测的需求、CI 必须绿的 PR，都是这个范式。

维度 目标驱动式 Agent Vibe Coding
输入 目标 + 约束 + 验收标准 感觉 + 模糊描述
验证者（verifier） 程序：单测、类型检查、CI、断言 人：看一眼、跑一下、觉得对
终止条件 验收通过（客观） “看起来行了”（主观）
失败可见性 高（测试红/绿） 低（只有明显 bug 才暴露）
迭代成本 每次迭代有明确信号 每次迭代靠人肉判断，易陷入”越改越乱”
适用生命周期 长期维护的生产系统 短周期原型、一次性脚本、内部工具
对使用者的要求 会写验收标准 会描述需求 + 能判断”跑起来对不对”

用一句话概括差异：

目标驱动式 Agent 把”对不对”交给程序判定；Vibe Coding 把”对不对”交给人的直觉判定。

前者可规模化（可并行、可自动回归），后者不可规模化（人的注意力是瓶颈）。

4.3 90 天崩溃曲线：机制解释

公开数据里有一组很值得警惕的观察：Y Combinator 2025 冬季批次中，21% 的团队代码库超过 91% 由 AI 生成；到第 90 天，其中 40%–60% 的团队发现”修一个 bug 会破坏另外三个功能”，冲刺产能被稳定化工作吞噬，原始速度优势完全消失（人人都是产品经理，2026-08-12）。

这个曲线的机制不复杂，但常被归因为”模型不行”：

  1. 没有 verifier 的系统必然熵增。每加一个功能，隐含假设多一条，但没有测试把它钉住。
  2. AI 代码的维护成本 ≈ 阅读成本。Vibe Coding 没有消除阅读成本，只是把它外部化到未来（”技术债”的现代版）。
  3. 耦合是隐式产生的。人类写代码时会本能地避免过度耦合（因为要自己维护）；Agent 只对当前 prompt 负责，天然倾向于”能跑就行”的实现。
  4. 人的记忆是瓶颈。Vibe Coding 依赖你记得”上次那个地方是怎么改的”，而这个记忆在 3 周后必然失效。

所以 90 天不是玄学，是**”隐式假设 > 显式约束”的临界点**。

4.4 适用场景：按”可验证性 × 生命周期”切

生命周期短 生命周期长
可验证性高（有测试/有明确 IO） ✅ 非常适合 Vibe Coding（脚本、数据管道、内部工具） ⚠️ 可以用，但要逐步补测试，转目标驱动
可验证性低（UI/交互/业务规则模糊） ✅ 适合（原型、demo、一次性活动页） ❌ 高危（核心业务系统、金融/医疗逻辑）

明确不适合 Vibe Coding 的四类：

  1. 有合规/审计要求的系统（金融、医疗、车控）——你无法为”没读过的代码”签字；
  2. 多人长期协作的代码库——风格与隐式约定会失控；
  3. 性能/资源敏感路径——“能跑”和”跑得动”差一个数量级；
  4. 安全边界相关代码（认证、加密、权限）——LLM 生成的这类代码是漏洞高发区。

4.5 第三条路：SDD（规范驱动开发）

2026 年一个明显的趋势是 Spec-Driven Development 的回归：先写规范（需求 + 验收标准 + 边界条件），再让 Agent 实现（掘金，2026-07-14；掘金，2026-04-29）。

它的本质不是”新方法论”，而是把 verifier 前移：

SDD 解决的是目标驱动式 Agent 的前置成本问题：写测试比写 spec 贵，但写 spec 比”事后 debug”便宜。对 Coding Agent 尤其重要——**spec 是 Agent 唯一能稳定消费的”意图压缩包”**，比 20 轮对话澄清有效得多。

我的工程判断：Vibe Coding 适合探索期，SDD 适合交付期，两者不是替代关系，是阶段关系。 争论”该不该 Vibe Coding”没有意义，真正的问题是”你现在在哪个阶段”。

5. 选型建议

5.1 决策树（按约束排序，而不是按功能排序）

5.2 Claude Code vs Codex：不是”谁更强”，是”你的组织长什么样”

你的情况 建议 理由
深度终端用户、单机开发、重视可控与可回滚 Claude Code 终端体验、checkpoint、hooks 的确定性管控最成熟
团队已重度使用 GitHub + PR 流程 Codex 云端并行 + PR 自审 + AGENTS.md 与 GitHub 工作流贴合
需要同时派发多个任务、机器会被关掉 Codex Cloud 云端持久环境，任务不依赖本地机器在线
已有大量 Claude 订阅/合规审查通过 Claude Code 采购与合规路径已通，切换成本最低
要审代码安全、做仓库级扫描 Codex（+ Security CLI） 有专门的开源安全扫描形态
两者都想用 双轨：Claude Code 做探索与重构，Codex 做批量与 CI 现实中不少团队就是这么干的，成本可接受

一个务实的观察：这两个产品的差异，在 80% 的日常任务上小于”你有没有写好 CLAUDE.md / AGENTS.md”带来的差异。 先把仓库约定文件写好、把测试跑通，再纠结工具。

5.3 场景 → 推荐组合

场景 首选 备选 关键理由
单人全栈开发 Claude Code Codex CLI 上下文连续性 + 回滚
团队 PR 流水线 Codex Claude Code + CI 云端并行、GitHub 原生
遗留系统重构（10 万行+） Claude Code + subagents Codex Cloud 需要隔离探索上下文、逐步验证
从零做 MVP / 内部工具 Manus Codex / Claude Code 端到端交付，含部署与自测
数据不出内网 OpenClaw + 本地模型 Hermes MIT + 可接 Ollama/vLLM

企业规模化管控 Codex/Claude Code + OCE 自建网关 需要命名空间隔离、凭据管理、审计
非技术成员参与 Manus — 唯一不需要终端的选项

5.4 各自的短板（选之前必须接受的代价）

产品 最痛的三点
Claude Code ① 强绑定 Claude，模型换代你做不了主；② 长任务 token 消耗大，成本不可预测；③ 无自托管，合规只能靠合同
Codex ① Cloud 必须出网；② 云端环境准备有冷启动成本；③ PR 由 Agent 生成后，审查负担转移到人，团队容易”看着像对就 merge”
Hermes ① 生态早期，技能质量参差；② 自进化缺强制验证器，错误会固化；③ 效果强依赖你接的模型
OpenClaw ① 升级频繁破坏自定义工作流（社区真实抱怨）；② 默认宿主机权限，安全需自己兜；③ 插件/技能质量无门槛
Manus ① 纯黑箱，不可本地、不可审计；② 私有仓库/内网依赖基本无解；③ 积分计费，长任务失败重试成本不透明

5.5 组合策略：两条被验证过的路径

路径 A：能力分层（推荐给 10 人以上团队）

理由：探索期用容忍度高、产出快的工具；实现期用可控、可回滚的工具；把关期必须有程序化 verifier + 人。

路径 B：双 Agent 交叉验证（推荐给关键模块）

让 Claude Code 写实现，Codex 做 review（或反过来）。两个异构模型的盲区不重合，实测能捞出一批单模型自审漏掉的问题。代价是成本翻倍，只对核心模块值得。

6. 工程踩坑点

6.1 通用坑（与选哪个产品无关）

坑 表现 修法
把 Agent 当 autocomplete 只给一句话需求，期待它猜对 给目标 + 约束 + 验收标准（SDD）
没有 verifier 改完不知道对不对，靠肉眼 先补测试/类型检查/CI，再上 Agent
仓库约定文件缺失 每次都要重复交代规范 写 CLAUDE.md / AGENTS.md，进版本库
上下文塞满 把所有文档贴进 prompt 分层：常驻约定 < 200 行；其余按需检索
自动批准所有命令 --dangerously-skip-permissions 常态化 白名单 + hook 拦截危险命令
benchmark 选型 按榜单分数决策 用自己仓库的 20 个真实任务做 A/B
忽略缓存成本 每轮重排上下文，prompt cache 全 miss 稳定前缀，易变内容放尾部

6.2 分产品坑

Claude Code

  • CLAUDE.md 膨胀：写着写着变成 500 行，反而稀释注意力。控制在 100–200 行，只放”模型猜不到的东西”（构建命令、目录约定、禁忌）。
  • Subagent 黑箱：子 Agent 只回结论不给证据，主 Agent 无法校验。要求它回传”结论 + 依据文件 + 置信度”。
  • Hooks 写太狠：每个工具调用都跑一遍格式化 + lint，长任务直接卡死。只对写操作挂 hook。
  • 跳过权限确认：省事，但一次提示注入就可能是 rm -rf。

Codex

  • 云端环境不一致：本地能跑、云端装不上依赖（私有包、系统库）。提前用容器固化环境。
  • PR 洪水：并行派发 10 个任务 → 10 个 PR → 没人认真看。限制并发数，强制”人审 + CI 双绿”。
  • AGENTS.md 与实际不符：写了但过期，Agent 会照着错的做。当成代码维护，改流程必须同步改它。

Hermes

  • 技能库污染：自动生成的技能没有验证，错的一次成功就被固化。加”技能准入”：必须带样例输入输出 + 通过一次回归。
  • 自进化不可控：策略库在你不注意时漂移。定期导出 diff 审计。
  • 弱模型放大错误：本地小模型 + 自进化 = 错误自我强化。要么用强模型，要么关掉自动演化。

OpenClaw

  • 升级破坏工作流：这是社区最集中的抱怨——几乎每次升级都要修环境，有人因此转向托管产品（36氪，2026-10-12）。锁版本 + 升级前备份 + 在测试机先跑一周，不要追最新。
  • 默认宿主机权限：官方明确主会话工具直接跑在宿主机。开沙箱，或至少用独立用户 + 容器。
  • 多通道路由混乱：同时接 5 个聊天软件后，会话串线、权限错配。按通道划分 workspace。
  • token 成本失控：常驻 Agent + 高频消息 = 账单不可预测。设日预算上限。

Manus

  • 长任务失败成本：跑到 90% 失败，重试要重花积分。把大任务拆成可交付的小段。
  • 不可审计：出问题看不到中间过程。关键产物要求它输出变更说明与验证记录。
  • 数据边界：上传的仓库/数据在云端，先过一遍合规。

6.3 一条被低估的踩坑：把”工具数量”当能力

OpenClaw 装了 80 个 skill、Claude Code 接了 30 个 MCP server——结果是选择准确率下降 + 上下文被描述占满。判断标准应该是：最近 30 天真正被调用过的工具/技能有几个，其余的归档。工具集的健康度看”命中率”，不看”库存量”。

7. 小结

  1. 这五者不在同一生态位。 Claude Code / Codex 是垂直编码产品，比的是 harness 打磨程度；OpenClaw / Hermes 是可自托管的 Agent 运行时，比的是编排能力与生态；Manus 是通用任务 Agent，比的是端到端交付。跨生态位比”谁更强”没有意义。
  2. 决定编码 Agent 体验的是 harness，不是模型分数。 同一模型换 harness，长任务成功率能差数十个百分点。榜单分数衡量的是”模型 + 官方 harness”，不是你的集成效果。
  3. 本地部署的真正判据是”推理是否出网”，不是客户端是否开源。 要内网就得接受本地模型的能力折损；两者不可兼得。
  4. 长代码库理解有三条路线，没有普适最优。 仓库规范好 → agentic search 性价比最高；命名混乱的老仓库 → 先补类型与命名，比换工具收益大。
  5. MCP 收敛了工具层，没收敛流程层。 工具越多选择越难，工具集要策展不要堆砌；Skills 的价值在于”不必每次重组工具”。
  6. 调试能力的本质是能否闭合 verify loop。 Manus 的浏览器自测很强但不可观测，Claude Code 的 verifier 要自己配但每一步可见可回滚——生产环境通常后者更重要。
  7. Vibe Coding 的判别标准在验收侧，不在输入侧。 用自然语言写代码不算 Vibe Coding，放弃阅读代码、把 verifier 换成人眼才算。它的适用边界由”可验证性 × 生命周期”决定。
  8. 90 天崩溃不是模型问题，是”隐式假设超过显式约束”的临界点。 Vibe Coding 没有消除阅读成本，只是把它外部化。
  9. 选型的正确顺序是：先定数据边界 → 再定工作流形态 → 最后才比功能。 反过来做，一定选到”功能最全但用不起来”的那个。
  10. 先写好 CLAUDE.md/AGENTS.md、把测试跑通，再纠结工具。 这两件事的收益，大于在 Claude Code 和 Codex 之间反复横跳。

如果只留一句：编码 Agent 的上限由模型决定，下限由 harness 和 verifier 决定——而生产环境里，你感受到的几乎全是下限。
